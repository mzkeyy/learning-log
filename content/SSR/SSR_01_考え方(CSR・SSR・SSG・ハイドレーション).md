## 描き方の4つ
| 方式 | HTML を作る場所・タイミング | 最初の表示 | 向く場面 |
| --- | --- | --- | --- |
| **CSR**(SPA) | ブラウザで、JS が動いてから | 遅い(白い画面 → 表示) | ログイン後の管理画面、SEO 不要 |
| **SSR** | サーバーで、リクエストのたびに | 速い | ユーザーごとに違うページ、SEO が要る |
| **SSG**(静的生成・プリレンダー) | ビルド時に1回 | 一番速い(CDN から) | ブログ・ドキュメント・LP |
| **ストリーミング SSR** | サーバーで、できた所から少しずつ | 速い(遅い部分は後から) | 一部だけ遅いデータがあるページ |
- **どの方式でも、表示したあとはブラウザ側で動く**(ボタン・画面遷移)。違うのは「最初の HTML」
- ISR(一定時間ごとに作り直す SSG)は SSG と SSR の中間。CDN のキャッシュ(`s-maxage` + `stale-while-revalidate`)でも似たことができる

## CSR の流れ(比較のため)
```html
<!-- サーバーが返す HTML(中身は空) -->
<div id="root"></div>
<script type="module" src="/app.js"></script>
```
```
1. 空の HTML を受け取る            → 白い画面
2. app.js(数百 KB)をダウンロード
3. JS を実行して画面を描く         → やっと枠が出る
4. API からデータ取得              → 「読み込み中…」
5. データが来て描き直す            → やっと中身が出る
```
- 検索エンジンや SNS のプレビュー(OGP)は、JS を実行しないか遅いことがある → 中身が見えない

## SSR の流れ
```
1. サーバーでデータを取得し、React で HTML を作る
2. 中身入りの HTML を返す           → すぐ読める(まだボタンは動かない)
3. ブラウザが JS をダウンロード
4. ハイドレーション                 → ボタンなどが動くようになる
```
| 指標 | CSR | SSR |
| --- | --- | --- |
| 中身が見えるまで(LCP) | 遅い | **速い** |
| サーバーの負担 | ほぼなし(静的ファイル) | リクエストごとに描画 |
| 操作できるまで(INP に影響) | JS 実行後 | JS 実行後(**同じ JS は結局要る**) |
| SEO・OGP | 弱い | 強い |
→ 指標の意味 [[Webパフォーマンスとアクセシビリティ]]

## ハイドレーションとは
サーバーで作った HTML は**ただの文字**。イベント(クリックなど)は付いていない。ブラウザで同じコンポーネントをもう一度動かして、**既にある DOM にイベントと状態をつなぐ**のがハイドレーション。
```
サーバー:  <button>0 回クリック</button>   ← 見た目だけ
             ↓ JS が読み込まれる
ブラウザ:  hydrateRoot(root, <App />)
           React が DOM を作り直さずに「この button はこのコンポーネント」と対応づける
           onClick が付き、useState が動き始める
```
- **作り直さない**ので速い。そのかわり、**サーバーとブラウザで同じ HTML になる**必要がある。違うとエラーになり、その部分をブラウザで描き直す → [[SSR_05_ハイドレーションエラーと注意点(XSS・キャッシュ・状態)]]
- JS が届くまではボタンを押しても何も起きない(フォームはふつうの `<form>` として送れるようにしておくと安心 = 段階的な強化)

### サーバーとブラウザで動くもの
| コード | サーバー(SSR) | ブラウザ |
| --- | --- | --- |
| コンポーネントの本体(return まで) | 動く | 動く |
| `useState` の初期値 | 動く | 動く |
| `useEffect` / `useLayoutEffect` | **動かない** | 動く(ハイドレーション後) |
| イベントハンドラ(`onClick`) | 動かない | 動く |
| `window` / `document` / `localStorage` | **ない**(触るとエラー) | ある |
- ブラウザだけの処理は `useEffect` の中に書く。これが SSR の基本ルール

## ストリーミングと Suspense
```
従来の SSR:  一番遅いデータを待ってから、全部まとめて送る
ストリーミング:
  1. 枠(シェル)と速いデータの部分を先に送る      → すぐ表示
  2. 遅い部分は <Suspense fallback> の「読み込み中…」を送っておく
  3. データがそろったら、その部分の HTML を同じ接続で追加で送る → 差し替わる
```
- ハイドレーションも部分ごとに進む(選択的ハイドレーション)。ユーザーが触った部分が先に動くようになる
- 詳しく → [[SSR_03_ストリーミングSSR(renderToPipeableStream・Suspense)]]

## 選び方
```
SEO・OGP が要る / 最初の表示を速くしたい?
 ├─ いいえ → CSR(Vite + React)で十分。シンプルで安い
 └─ はい
     ├─ 全員に同じ内容・更新は少ない → SSG
     ├─ ユーザーごと・頻繁に変わる → SSR
     └─ 一部だけ遅い → ストリーミング SSR
```
- フレームワークなら**ページごとに混ぜられる**(LP は SSG、マイページは SSR、管理画面は CSR)
- React Server Components は「サーバーだけで動き、JS を送らないコンポーネント」。SSR とは別の仕組みで、組み合わせて使う → [[SSR_06_静的生成とフレームワーク(prerender・React Router・Next.js・RSC)]]
