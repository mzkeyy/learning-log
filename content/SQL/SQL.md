## まず一言で
> **SQL は「どうやって取るか」ではなく「何が欲しいか」を書く言語(宣言型)。**
> 手順はデータベースが考えてくれる。だから短く書けるが、**WHERE を忘れた UPDATE / DELETE は全行に効く**。

## 全体像
```
[アプリ(Next.js / Workers など)]
        │ SQL 文を送る  例: SELECT * FROM users WHERE id = ?
        ▼
[データベース(PostgreSQL / MySQL / SQLite / D1)]
   ├─ users テーブル   ┌────┬───────┬──────────────┐
   │                   │ id │ name  │ email        │ ← 列(カラム)
   │                   ├────┼───────┼──────────────┤
   │                   │ 1  │ 田中  │ a@example.com│ ← 行(レコード)
   │                   └────┴───────┴──────────────┘
   └─ orders テーブル  (user_id で users とつながる)
        │ 結果(表の形)を返す
        ▼
[アプリが画面に表示]
```

## 用語の地図
| 用語 | 一言 |
| --- | --- |
| **RDB(リレーショナルデータベース)** | データを「表(テーブル)」で持ち、表同士を関連づけるデータベース |
| **テーブル / 行 / 列** | 表 / 1件のデータ / 項目 |
| **主キー(PRIMARY KEY)** | 行を一意に特定する列。普通は `id` |
| **外部キー(FOREIGN KEY)** | 別テーブルの主キーを指す列。`orders.user_id → users.id` |
| **クエリ** | データベースへの問い合わせ(SQL 文) |
| **JOIN** | テーブル同士をつなげる |
| **インデックス** | 検索を速くする索引。本の巻末索引と同じ |
| **トランザクション** | 複数の処理を「全部成功 or 全部なかったこと」にするまとまり |
| **マイグレーション** | テーブル構造の変更を履歴として管理する仕組み |
| **ORM** | SQL を書かずにプログラムの関数でDB操作する道具(Prisma・Drizzle など) |

## よく使う構文 早見表
```sql
-- 取り出す
SELECT name, email FROM users WHERE age >= 20 ORDER BY created_at DESC LIMIT 10;
-- 集計する
SELECT user_id, COUNT(*) AS 件数, SUM(amount) AS 合計 FROM orders GROUP BY user_id;
-- つなげる
SELECT u.name, o.amount FROM orders o JOIN users u ON o.user_id = u.id;
-- 追加・更新・削除(WHERE を必ず確認!)
INSERT INTO users (name, email) VALUES ('田中', 'a@example.com');
UPDATE users SET name = '佐藤' WHERE id = 1;
DELETE FROM users WHERE id = 1;
```

## SELECT の書く順番と実行される順番
| 書く順 | 実行される順 |
| --- | --- |
| 1. SELECT | 1. FROM / JOIN(どの表から) |
| 2. FROM / JOIN | 2. WHERE(行を絞る) |
| 3. WHERE | 3. GROUP BY(グループにまとめる) |
| 4. GROUP BY | 4. HAVING(グループを絞る) |
| 5. HAVING | 5. SELECT(列を選ぶ・計算する) |
| 6. ORDER BY | 6. ORDER BY(並べる) |
| 7. LIMIT | 7. LIMIT(件数を切る) |

→ 「WHERE で SELECT の別名(AS)が使えない」「集計結果の絞り込みは HAVING」などの理由はこの順番で説明できる。

## 主なデータベース製品
| 製品 | 特徴 | よく出会う場面 |
| --- | --- | --- |
| **PostgreSQL** | 高機能・標準に忠実。迷ったらこれ | Supabase・Neon・Vercel Postgres |
| **MySQL** | 歴史が長く利用者が多い | WordPress・PlanetScale |
| **SQLite** | ファイル1つで動く軽量DB。サーバー不要 | スマホアプリ・Cloudflare D1・Turso |
| **SQL Server / Oracle** | 企業向け商用 | 大企業の基幹システム |

方言(製品ごとの差)はあるが、この連載の構文はほぼ共通。違いが出やすいのは日付関数・`LIMIT` の書き方・自動採番(`AUTOINCREMENT` / `SERIAL` / `AUTO_INCREMENT`)など。

### SQLite と MySQL / PostgreSQL の違い ― サーバーを挟むかどうか
「SQLite はファイル、MySQL はサーバー」と言われるが、本当の違いは **サーバー(別のプログラム)を挟むかどうか**。
```
【MySQL / PostgreSQL】クライアント・サーバー型
[アプリ] ──ネットワーク(ポート3306など)──▶ [MySQLサーバー(常駐プロセス)] ──▶ [データファイル群]
          ユーザー名・パスワードで接続

【SQLite】組み込み型
[アプリ + SQLiteライブラリ] ──直接読み書き──▶ [app.db(ファイル1つ)]
```
- **MySQL** もデータは最終的にディスク上のファイルに保存している。ただしアプリがそのファイルを直接触ることはなく、常駐しているサーバーに SQL を送り、サーバーがファイルを読み書きする
- **SQLite** はサーバーがない。アプリに組み込まれたライブラリが `.db` ファイルを直接読み書きする

| | SQLite | MySQL / PostgreSQL |
| --- | --- | --- |
| 形態 | ライブラリ(アプリに組み込む) | サーバー(別プロセスで常駐) |
| データ | **ファイル1つ**(`app.db`) | サーバーが管理する複数のファイル |
| 接続 | ファイルのパスを指定するだけ | ホスト・ポート・ユーザー・パスワード |
| セットアップ | ほぼ不要(Mac には最初から入っている) | インストールして起動・設定が必要 |
| バックアップ | ファイルをコピーすればよい(書き込み中は専用の方法を使う) | `mysqldump` などの専用ツール |
| 同時書き込み | **書き込めるのは同時に1つだけ**(読み込みは並行できる) | 多数の同時書き込みに強い |
| 複数サーバーからの利用 | 苦手(ファイルは1台のマシンにあるため) | 得意(ネットワーク越しに接続できる) |
| 得意な用途 | スマホアプリ、デスクトップアプリ、小〜中規模の Web、テスト | 多くの人が同時に書き込む Web サービス |

#### 補足:Cloudflare D1 の場合
D1 の中身は SQLite だが、**Cloudflare がサービスとして運用** している。
- 自分でファイルを触ることはなく、Workers から `env.DB.prepare(...)` で操作する
- 書き込める場所は1か所(プライマリ)で、読み取り用の複製を世界各地に置ける
- SQL の書き方は SQLite、使い勝手はサーバー型に近い、という中間的な存在

**まとめ**:SQLite は「ファイルを直接読み書きするライブラリ」、MySQL は「サーバーを通してファイルを管理する」もの。そのため SQLite は手軽だが、大量の同時書き込みは苦手。
