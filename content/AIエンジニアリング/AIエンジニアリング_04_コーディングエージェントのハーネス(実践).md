Claude Code・Codex などで AI にコードを書かせるとき、**リポジトリと開発環境の側で用意する「自分たちのハーネス」**の作り方。個別のツールの使い方は [[Claude Code]] / [[Codex]]。

## 1. リポジトリを「AI が読める」状態にする
OpenAI の実験(2026年2月、人が1行も書かずに製品を作った)で効いたこと。
- **リポジトリを唯一の情報源**にする: 設計・計画・決定・技術的負債をリポジトリの中に置き、版管理する(チャットや社内 Wiki だけにしない)
- **AGENTS.md / CLAUDE.md は「地図」**: 全部を書くのではなく、短く(100行程度)して「どこに何が書いてあるか」を示す。詳細は `docs/` に
```
AGENTS.md (CLAUDE.md)     … 短い地図: 構成・コマンド・どこを読めばいいか・守るべき原則
ARCHITECTURE.md           … 全体の構成と依存の方向
docs/
├── design/               … 設計ドキュメント
├── adr/                  … 決定の記録(ADR)
├── plans/                … 進行中・完了した作業計画
└── ...
```
- 使い分け → [[mdファイル使い分け]] / [[04_CLAUDE.mdとメモリ]] / [[Codex_03_AGENTS.mdとconfig.toml]]

## 2. ルールは文章でなく、機械で守らせる
| 守らせたいこと | ガイド(文章) | センサー(機械) |
| --- | --- | --- |
| コードの書き方 | 「この書き方で」 | **lint・formatter**(Biome / ESLint)→ [[モノレポ_04_品質のツール(Biome・ESLint・TypeScript・Changesets)]] |
| 型の正しさ | — | **型チェック**(`tsc --noEmit`) |
| 動作 | 「壊さないで」 | **テスト**(単体・結合・E2E)→ [[テスト]] |
| 層・依存の方向 | ARCHITECTURE.md | **構造のテスト**(依存のルールの lint、import の禁止) |
| ドキュメントの同期 | 「直したら docs も」 | docs とコードがずれたら落ちるテスト |
| 秘密情報 | 「コミットしない」 | 秘密情報のスキャン・pre-push フック |
- エラーメッセージに**直し方**を書いておくと、エージェントが自分で直せる(lint のメッセージに「代わりに〇〇を使う」)
- 実行するコマンドを AGENTS.md に書く(`pnpm test`、`pnpm check`)

## 3. 検証手段を渡す(一番効く)
- 「テストを書いて、通るまで直して」「画面をスクショして期待と比べて」のように、**エージェントが自分で確かめられる**状態にする → [[07_ベストプラクティス]]
- Web アプリなら**ブラウザを操作して確かめる**手段(Playwright・ブラウザ操作の MCP)を渡す。単体テストや curl だけでは見落とす不具合がある
- Hooks で「編集したら lint・テストを実行」→ [[11_Hooks]]

## 4. 長時間の作業のハーネス
Anthropic の実験(2025年11月)で効いた形。エージェントは**セッションごとに記憶がない**ので、ファイルで引き継ぐ。
| 役割・道具 | 内容 |
| --- | --- |
| **初期化役**(最初の1回) | 環境の準備: 起動スクリプト(`init.sh`)、進捗ファイル、機能一覧、最初のコミット |
| **機能一覧**(JSON) | 作るべき機能を全部書き出し、最初は全部「未完了」。エージェントは**完了の印だけ**を変えてよい(テストや項目を消したり書き換えたりしない) |
| **進捗ファイル + git** | 毎セッションの最後に何をしたかを書き、説明付きでコミット。悪い変更は git で戻せる |
| **作業役**(毎回) | 始めに: 場所の確認 → 進捗と git log を読む → 機能一覧を見る → 基本の動作確認。それから**1回に1機能**だけ進める |
| よくある失敗 | 早すぎる「完成しました」/ 動作確認なしで完了扱い / 環境を壊したまま終わる → 機能一覧・自分での確認・始めと終わりの動作確認で防ぐ |

## 5. 作る役と評価する役を分ける
Anthropic の実験(2026年3月)の3つの役割の構成。
```
計画役(Planner):  短い依頼 → 製品の仕様に広げる(技術の細部には踏み込みすぎない)
       │
生成役(Generator): 仕様に沿って作る。区切りごとに自分でも確認
       │ ▲ 差し戻し
評価役(Evaluator): 実際にブラウザで操作して、基準ごとに採点。基準を下回れば不合格
```
- 1人のエージェントで作らせた場合、見た目はできていても**中心の機能が動かない**ことがあった
- 作業の前に、生成役と評価役が「何を作り、どう確かめるか」を**合意**してから進める(ファイルでやり取り)
- 評価の基準は具体的に(例: デザインの一貫性・独自性・作りの丁寧さ・使いやすさ)。モデルが元々得意な項目より、苦手な項目に重みを付ける
- モデルが良くなると不要になる部品もある(区切りごとの進め方は、新しいモデルでは外された)。計画役と評価役は残った

## 6. ドキュメントの「庭の手入れ」
- コードとずれた古いドキュメントは、エージェントを間違った方向に導く
- **定期的に、ずれたドキュメントや規則違反を探して直す作業**(人でも、バックグラウンドのエージェントでも)
- AI が生む小さな負債(重複・使われないコード・方針違反)も、溜める前にこまめに片付ける

## 7. 並列と人の役割
- 複数のエージェントを並列で動かす(worktree・クラウドのセッション)→ [[14_並列作業(Worktree・Agent View・Workflows)]]
- 人の仕事は「コードを書く」から**「環境を整え、意図を伝え、結果を確かめる」**へ
  - 仕様・優先度・受け入れ基準を決める
  - ハーネス(ルール・テスト・ドキュメント)を改善する
  - 差分をレビューする(**AI がテストを消していないか・skip していないか・期待値を書き換えていないか**)

## チェックリスト
- [ ] AGENTS.md / CLAUDE.md は短い地図で、詳細は docs/ にある
- [ ] lint・型チェック・テストが1コマンドで動き、エージェントが実行できる
- [ ] 層・依存のルールが機械でチェックされる
- [ ] Web アプリならブラウザで動作確認する手段がある
- [ ] 長い作業は、計画・進捗・機能一覧をファイルで引き継ぐ
- [ ] 重要な成果物は別の役(テスト・評価役・人)が評価する
- [ ] 危険な操作はサンドボックス・権限・承認で止まる
- [ ] ドキュメントとコードのずれを定期的に直している
