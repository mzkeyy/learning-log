基本の考え方は [[AIアプリ開発_07_評価・コスト・セキュリティ・運用]]。ここでは**評価の仕組みをどう作り、どう回すか**を深掘りする。

## なぜ評価が中心なのか
- LLM の出力は確率的で、**1回うまくいっても次も同じとは限らない**
- プロンプト・コンテキスト・ハーネス・モデルを変えたとき、**良くなったか悪くなったか**は評価でしかわからない
- 評価がないと、「ある質問は直ったが、別の質問が壊れた」に気づけない
- 評価は AI 開発における**テストとベンチマーク**。最初に作り、ずっと育てる

## 評価セットの作り方
| 手順 | 内容 |
| --- | --- |
| 1. 何を測るか決める | 正確さ・根拠に基づくか・形式・安全・口調・タスクの完了率など。**1つの評価で1つの観点** |
| 2. 入力を集める | **本番のログ**(一番価値がある)、実際の失敗例、人が書いた例、AI で作った例(偏りに注意) |
| 3. 期待する結果を決める | 正解 / 必ず含むべきこと / 採点の基準(ルーブリック) |
| 4. 分ける | 改善に使う(開発用)と、最終確認用(**改善に使わない**テスト用)に分ける。テスト用に合わせて調整すると過学習になる |
- 最初は**20〜50件**でよい。簡単すぎるもの・難しすぎるものばかりにしない
- 失敗した本番の事例を見つけるたびに**評価セットに足す**(回帰テストと同じ)
- 分布を本番に合わせる(よくある質問が多く、珍しいものは少なく)

## 採点の方法
| 方法 | 向くもの | 注意 |
| --- | --- | --- |
| **コードで判定** | 分類の正解、JSON のスキーマ、数値、必須の語、ツールを正しく呼んだか | 一番安くて確実。できるものは全部これで |
| **LLM に採点させる** | 文章の質、根拠に基づくか、指示に従ったか | 採点役の**基準を具体的に**、採点役自体を人の判断と照らし合わせて確かめる |
| **ペアで比較** | 新旧どちらが良いか | 絶対評価より安定しやすい。順番の偏りに注意(入れ替えて2回) |
| 人の採点 | 最初の基準づくり、難しい判断、最終確認 | 遅く高い。一部をサンプルで |
| **実行して確かめる** | コード生成(テストが通るか)、エージェント(タスクが完了したか) | 一番信頼できる。環境の準備が必要 |

### LLM-as-judge(AI に採点させる)のコツ
- 「良いか悪いか」ではなく、**項目ごとに具体的な基準**(例: 「質問に答えている」「資料にないことを言っていない」「200字以内」)
- 点数より **合格 / 不合格** の判定のほうが安定しやすい
- 理由を先に書かせてから判定させる
- 採点役のモデル・プロンプトも固定して記録する(変えたら点数の意味が変わる)
- 時々**人の判定と比べて**、採点役がずれていないか確かめる

## 改善のループ
```
評価セットで今の点数を測る(基準値)
   ↓
失敗した例を読む(★ 数字だけ見ない。実際の出力を読む)
   ↓
原因の仮説 → 1つだけ変える(プロンプト / コンテキスト / ツール / ハーネス / モデル / effort)
   ↓
開発用セットで測る → 良くなったら採用、悪くなったら戻す
   ↓
定期的にテスト用セットで確認(過学習していないか)
```
- **一度に1つだけ変える**(何が効いたかわからなくなる)
- 確率的なので、**同じ入力を複数回**実行して平均・ばらつきを見る
- コストと遅延も一緒に記録する(良くなっても高すぎたら意味がない)
- 変更のたびに記録を残す(何を変えて、何点になったか)

## エージェントの評価
| 観点 | 例 |
| --- | --- |
| タスクの完了 | テストが通った、チケットの要件を満たした |
| 道のり | 無駄なツール呼び出し、遠回り、同じことの繰り返し |
| 安全 | 許されない操作をしなかった、承認を求めた |
| コスト・時間 | トークン・ツール呼び出しの回数・かかった時間 |
- 結果だけでなく**トレース(何をしたか)**を見る → [[オブザーバビリティ_04_トレースとOpenTelemetry]]
- 公開のベンチマーク(SWE-bench など)の点数より、**自分たちのタスクでの評価**のほうが判断に使える

## CI に組み込む
- プロンプト・モデル・ツールを変える PR では、**評価を自動で回して点数を表示**する
- 点数が一定以上下がったらマージしない(閾値はばらつきを見て決める)
- 実際に API を呼ぶので**お金がかかる**。PR では小さいセット、定期実行で大きいセット
→ [[Cicdパイプライン]] / [[テスト_06_実務(CI・不安定なテスト・AIとテスト)]]

## 本番での評価
| 方法 | 内容 |
| --- | --- |
| ユーザーの反応 | 👍👎、再生成・コピー・離脱 |
| サンプルを採点 | 本番の一部を LLM-as-judge で採点し続ける |
| A/B テスト | 新旧のプロンプト・モデルを一部の利用者で比べる |
| 失敗を評価セットへ | 本番の失敗 → 評価セットに追加 → 直す → 再発防止 |
→ [[AIエンジニアリング_06_本番運用(ガードレール・監視・モデル更新)]]

## 道具
- 自前のスクリプト(入力の一覧 → 実行 → 採点 → 結果の表)で十分始められる
- 評価・トレースの道具: Langfuse、LangSmith、Braintrust、Promptfoo、Arize など
- Claude Code の `claude-api` スキルには、評価セットを作る・評価に対して改善を回す手順も用意されている
