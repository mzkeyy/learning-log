出題分野「コストを最適化したアーキテクチャの設計」は 20%。他の分野の問題でも「最もコスト効率が高い」が条件になることが多い。

## 料金の基本
- **データ転送**:AWS に入る通信は無料。**インターネットへ出る通信は有料**。AZ 間・リージョン間も有料
  - 同じ AZ・プライベート IP 同士は無料
  - CloudFront から出すと、S3 から直接出すより安くなることが多い
- **NAT ゲートウェイ**は時間料金 + 処理したデータ量で意外と高い → S3・DynamoDB 宛は**ゲートウェイエンドポイント(無料)**
- **停止した EC2** はインスタンス料金はかからないが **EBS と Elastic IP は課金**される

## 分野ごとのコスト削減策
| 分野 | 削減策 |
| --- | --- |
| **EC2** | 常時稼働 → Savings Plans / RI。中断 OK → スポット。**Compute Optimizer** でサイズを適正化。夜間は止める(Instance Scheduler) |
| **コンテナ・Lambda** | Fargate Spot、Compute Savings Plans、Lambda を Graviton(Arm)で |
| **Graviton**(Arm の CPU) | 同じ性能で x86 より安いことが多い |
| **S3** | ライフサイクルルール、Intelligent-Tiering、**S3 Storage Lens** で分析 |
| **EBS** | gp2 → **gp3** に変える。使っていないボリューム・古いスナップショットを消す |
| **DB** | RI、Aurora Serverless v2(使わない時間に縮む)、DynamoDB のオンデマンド ⇔ プロビジョンドの見直し |
| **転送** | CloudFront、VPC エンドポイント、同じ AZ に置く |
| **分析** | Athena は Parquet + パーティションでスキャン量を減らす |

### スポットをうまく使う
- **EC2 フリート / Auto Scaling の混合インスタンスポリシー**:オンデマンドを最低限 + 残りはスポット、複数のインスタンスタイプを指定して中断に備える
- 中断されると困る処理(DB、長時間止められない処理)には使わない

## コスト管理のサービス
| サービス | 用途 | キーワード |
| --- | --- | --- |
| **Cost Explorer** | 過去の料金をグラフで分析、今後を予測、RI/SP のおすすめ | 「何にお金がかかっているか」 |
| **AWS Budgets** | 予算を決めて、超えそうになったら通知・アクション | 「予算超過でアラート」 |
| **Cost and Usage Report(CUR)/ Data Exports** | 一番細かい利用データを S3 に出力 → Athena で分析 | 「詳細な請求データ」 |
| **コスト配分タグ** | タグ(部署・プロジェクト)ごとに料金を分ける | 「部署ごとに請求を分けたい」 |
| **Compute Optimizer** | EC2・EBS・Lambda のサイズのおすすめ | 「オーバースペック」 |
| **Trusted Advisor** | 使っていないリソースなどを指摘 | — |
| **Organizations の一括請求** | 複数アカウントの利用量を合算してボリューム割引、RI/SP を共有 | — |
| **Pricing Calculator** | 構成の見積もり | — |

## 「一番安い」選択肢の選び方
1. **要件を満たさない選択肢をまず消す**(耐久性・可用性・速度の条件)
2. 残りから、**サーバーレス・マネージド・低頻度クラス・スポット**など安いものを選ぶ
3. ただし「データを失ってはいけない」のに One Zone-IA、「中断できない」のにスポット、などは**ひっかけ**

## 確認ポイント
- [ ] インターネットに出る通信は有料、入る通信は無料と言える
- [ ] NAT の料金を下げる方法(ゲートウェイエンドポイント)を言える
- [ ] gp2 → gp3 の変更でコストが下がることを知っている
- [ ] Cost Explorer・Budgets・Compute Optimizer の違いを言える
