**業務(ドメイン)の知識をそのままコードの形にして、複雑な業務ルールを扱えるようにする設計の考え方**。2003年に Eric Evans が著書『Domain-Driven Design』(通称エヴァンス本・青本)で提唱した。特定のフレームワークや技術ではなく、**「業務の専門家と開発者が同じ言葉で話し、その言葉どおりにコードを書く」ための考え方と道具箱**。

生成AIと開発する初学者向けに、「DDD の用語が出てきても分かる」「自分のアプリにどこまで取り入れるか判断できる」ことを目標に整理したノート群の入口。

## まず一言で
> **DDD は「コードの書き方」より先に「業務を正しく理解し、言葉と境界を揃える」ための方法。**
> 部品(エンティティ・リポジトリ…)だけ真似しても効果は薄い。逆に、**単純な CRUD アプリに全部入れると層が増えるだけで遅くなる**。

## 全体像
```
              ┌──────────────── 戦略的設計(大きな地図) ────────────────┐
              │  ドメイン(業務全体)                                      │
              │   ├─ コアドメイン      … 競争力の源泉。ここに DDD を全力投入 │
              │   ├─ 支援サブドメイン  … 必要だが差別化しない                │
              │   └─ 汎用サブドメイン  … 認証・決済など。既製品を使う        │
              │                                                          │
              │  [注文コンテキスト] ──連携── [配送コンテキスト]             │
              │     ↑ 境界づけられたコンテキスト(言葉の意味が通じる範囲)  │
              └──────────────────────────────────────────────────────────┘
                                  │ 各コンテキストの中で
                                  ▼
              ┌──────────────── 戦術的設計(部品) ────────────────┐
              │  集約 = エンティティ + 値オブジェクト(整合性の単位)  │
              │  リポジトリ(集約の保存・取得)                       │
              │  ドメインサービス / ドメインイベント                   │
              └──────────────────────────────────────────────────┘
              すべての土台: ユビキタス言語(業務の人とコードで同じ言葉を使う)
```

## 用語の地図
| 用語 | 一言 |
| --- | --- |
| **ドメイン** | ソフトウェアで扱う業務領域。例: EC の受注、病院の予約 |
| **ドメインエキスパート** | その業務に詳しい人(営業・現場担当・経理など) |
| **ドメインモデル** | 業務の概念とルールを整理して表現したもの。最終的にはコード |
| **ユビキタス言語** | チーム全員(業務の人+開発者)が会話・文書・コードで使う共通の言葉 |
| **境界づけられたコンテキスト** | ある言葉・モデルが一貫した意味を持つ範囲。システム分割の単位 |
| **サブドメイン(コア/支援/汎用)** | 業務を分けた領域と、その重要度 |
| **コンテキストマップ** | コンテキスト同士の関係図 |
| **エンティティ** | ID で見分けるもの。中身が変わっても同じもの(会員、注文) |
| **値オブジェクト** | 値そのもので見分けるもの。不変(金額、メールアドレス、住所) |
| **集約 / 集約ルート** | 一緒に整合性を守るオブジェクトのまとまり / その窓口 |
| **リポジトリ** | 集約を保存・取得する入れ物。DB の存在を隠す |
| **ドメインサービス** | どのエンティティにも自然に属さない業務ロジック |
| **ドメインイベント** | 業務上意味のある出来事(「注文が確定した」) |
| **アプリケーションサービス(ユースケース)** | 1つの操作の手順をまとめる係。業務ルール自体は持たない |
| **腐敗防止層(ACL)** | 外部システムの都合が自分のモデルに染み込まないよう翻訳する層 |

## DDD を使うべきか 早見表
| 状況 | おすすめ |
| --- | --- |
| フォーム入力→保存→一覧表示が中心(ブログ・管理画面・簡単な予約) | **使わない**。普通の CRUD でよい。ユビキタス言語だけ意識 |
| 業務ルールが多い・例外が多い(料金計算、在庫引当、審査フロー) | **戦術的設計を部分的に**(値オブジェクト・集約から) |
| 複数チーム・複数サービスで大きな業務を扱う | **戦略的設計から本格的に** |
| 期限が迫った小さな試作 | 使わない |

## DDD とよく一緒に出てくる言葉
| 言葉 | 関係 |
| --- | --- |
| クリーンアーキテクチャ / オニオン / ヘキサゴナル | ドメインを中心に置き、技術を外側に追いやる層構造。DDD と相性が良い(05章) |
| CQRS | 書き込み(コマンド)と読み取り(クエリ)でモデルを分ける(05章) |
| イベントソーシング | 状態ではなく「起きた出来事の列」を保存する。上級者向け |
| マイクロサービス | 境界づけられたコンテキストがサービス分割の目安になる |
| イベントストーミング | 付箋で業務の出来事を並べてモデルを発見するワークショップ |
