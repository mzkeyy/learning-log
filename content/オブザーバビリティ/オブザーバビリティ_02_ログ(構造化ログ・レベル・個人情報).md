## 構造化ログ(JSON で出す)
```ts
// ❌ 文章のログ: 人は読めるが、検索・集計しにくい
console.log(`User u_1 created order 123 (total 4500 yen)`)

// ✅ 構造化ログ: キーで検索・集計できる
console.log(JSON.stringify({
  level: 'info',
  event: 'order_created',
  requestId: 'req_8f2c',
  userId: 'u_1',
  orderId: '123',
  totalYen: 4500,
}))
```
- 「`event = order_created` で `totalYen > 10000`」のような検索ができる
- Cloudflare Workers Logs・CloudWatch Logs・Datadog などは JSON を**自動でフィールドに分解**してくれる
- **メッセージ文に値を埋め込まず、フィールドに分ける**のがコツ

## ログレベル
| レベル | いつ | 例 |
| --- | --- | --- |
| `debug` | 開発中の詳しい情報。本番では普段出さない | 関数の引数、SQL |
| `info` | 正常な重要な出来事 | ログイン成功、注文作成、ジョブ完了 |
| `warn` | 問題になりかけ・想定内の失敗 | リトライした、入力エラー、非推奨 API の利用 |
| `error` | 処理が失敗した。誰かが見る必要がある | 例外、外部 API の失敗、データ不整合 |
- 本番は `info` 以上が基本。**レベルを環境変数で切り替えられる**ようにする
- `error` を乱発しない(「入力が不正」はユーザーの問題なので `warn` か `info`)。error が多すぎると本当の問題が埋もれる

## 何を残すか
| 残す | 例 |
| --- | --- |
| **リクエスト ID / トレース ID** | 1つのリクエストのログをつなげる。レスポンスヘッダーにも返す(問い合わせ時に聞ける) |
| 誰が・何を | `userId`(内部 ID)、操作名、対象の ID |
| 結果 | 成功・失敗、ステータスコード、所要時間 |
| 失敗の理由 | エラーの種類・メッセージ・スタック、外部 API のエラーコード |
| 環境 | サービス名、バージョン(git のコミット)、リージョン |
- **アクセスログ**(全リクエストの メソッド・パス・ステータス・時間)は多くのプラットフォームが自動で出す。アプリは**業務上の出来事**を足す

## 残してはいけないもの
| ダメなもの | 代わりに |
| --- | --- |
| パスワード・API キー・トークン・Cookie・`Authorization` ヘッダー | 出さない(ライブラリの redact 機能で伏せる) |
| クレジットカード番号 | 出さない |
| 個人情報(氏名・メール・住所・電話) | 内部 ID で代用、必要なら一部を伏せる(`t***@example.com`) |
| リクエスト本文をまるごと | 必要な項目だけ |
| AI アプリの会話本文 | 原則残さないか、保存期間・閲覧権限を決めて別管理 |
- ログは**多くの人が見られて、長く残る**ので、漏えいの経路になりやすい → [[APIキー・シークレット管理]] / [[Webセキュリティ対策]]
- 保存期間を決めて、古いものは消す(費用と法令の両面)

## Node.js では pino が定番
```ts
import pino from 'pino'

export const logger = pino({
  level: process.env.LOG_LEVEL ?? 'info',
  redact: ['req.headers.authorization', 'req.headers.cookie', '*.password'],  // 伏せる
})

logger.info({ event: 'order_created', orderId: '123', userId: 'u_1' }, 'order created')
logger.error({ err, orderId: '123' }, 'payment failed')   // err はスタック付きで出る

// リクエストごとに ID を持った子ロガー
const log = logger.child({ requestId })
```
- JSON で速く出せる。開発中は `pino-pretty` で見やすく表示
- `console.log` でも JSON 文字列を出せば構造化ログになる(Workers はこれで十分)

## Hono でリクエスト ID 付きのログ
```ts
import { Hono } from 'hono'
import { requestId } from 'hono/request-id'

const app = new Hono()
app.use(requestId())   // X-Request-Id を受け取る or 新しく作る

app.use(async (c, next) => {
  const start = Date.now()
  await next()
  console.log(JSON.stringify({
    level: c.res.status >= 500 ? 'error' : 'info',
    event: 'http_request',
    requestId: c.get('requestId'),
    method: c.req.method,
    path: c.req.path,
    status: c.res.status,
    durationMs: Date.now() - start,
  }))
})
```

## ログの集め方
| 環境 | 仕組み |
| --- | --- |
| Cloudflare Workers | `console.log` → **Workers Logs**(`observability.enabled`)。外部へは OpenTelemetry 形式で送れる → [[オブザーバビリティ_05_道具と実装(Sentry・Cloudflare・AWS)]] |
| AWS | CloudWatch Logs(Lambda・ECS は標準出力が自動で入る)→ 長期保存は S3 → [[SAA_補足_ログのまとめ(種類・保存先・分析)]] |
| コンテナ・VM | **標準出力に出す**のが基本。収集はエージェント(OpenTelemetry Collector・Fluent Bit など)に任せる |
| 外部サービス | Datadog・Grafana Loki・Better Stack・Axiom など |
- アプリは**ファイルに書かず標準出力へ**(The Twelve-Factor App の考え方)。どこへ送るかは環境側で決める

## ログを見るとき
- まず**時間と requestId / traceId**で絞る
- 「いつから増えた?」→ デプロイの時刻と比べる(バージョンをログに入れておく)
- 同じエラーの件数を `event` や `error.type` で集計する
