## なぜ必要か
- 手元では動いていたのに、本番で「遅い」「たまに失敗する」「特定のユーザーだけおかしい」が起きる
- 本番のサーバーには入れない・デバッガも使えない(特にサーバーレスやエッジ)
- だから**動いている最中に情報を外に出しておき**、後から調べられるようにする
- ユーザーに言われる前に**自分で気づく**ためでもある

## 監視とオブザーバビリティの違い
| | 監視(モニタリング) | オブザーバビリティ |
| --- | --- | --- |
| 問い | 「決めておいた項目が正常か?」 | 「**想定していなかった**問題も、なぜ起きたか調べられるか?」 |
| 例 | CPU 90% 超えたら通知、サイトが 200 を返すか | 「このユーザーの決済だけ遅いのはなぜ?」をデータから追える |
| 道具 | 死活監視、閾値アラート | 構造化ログ・トレース・高い粒度の属性での検索 |
- 対立するものではなく、**監視 ⊂ オブザーバビリティ**くらいの関係。両方要る

## 3本柱の使い分け
```
メトリクス: 「エラー率が 5% に上がった」   ← 気づく(安い・全体像)
   ↓ どのリクエスト?
トレース:   「/api/checkout の決済 API 呼び出しが 8 秒かかって失敗」   ← 場所を特定
   ↓ 何が起きた?
ログ:       「payment_failed reason=timeout provider=stripe orderId=…」   ← 詳細を確認
```
| | ログ | メトリクス | トレース |
| --- | --- | --- | --- |
| 単位 | 1件の出来事 | 数値の集計 | 1リクエストの流れ |
| 量・費用 | 多い・高くなりがち | 少ない・安い | 中(サンプリングで調整) |
| 向くこと | 詳細の確認 | 傾向・アラート | 遅い箇所・失敗箇所の特定 |
- 3つを **トレース ID** でつなげると、メトリクス → トレース → ログと辿れる

## 何を見るか(定番の考え方)
### ゴールデンシグナル(Google SRE)
| シグナル | 意味 | 例 |
| --- | --- | --- |
| **レイテンシ** | 応答にかかる時間 | p95 が 300ms |
| **トラフィック** | どれだけ使われているか | 毎秒のリクエスト数 |
| **エラー** | 失敗の割合 | 5xx の割合 |
| **サチュレーション** | どれだけ余裕がないか | CPU・メモリ・DB 接続数の使用率 |
- API やサービスなら **RED**(Rate・Errors・Duration)、サーバーや DB などの資源なら **USE**(Utilization・Saturation・Errors)と覚える → [[オブザーバビリティ_03_メトリクスとアラート]]

## SLI・SLO・SLA
| 用語 | 意味 | 例 |
| --- | --- | --- |
| **SLI**(指標) | ユーザーの体験を表す数値 | 「成功したリクエストの割合」「300ms 以内に返った割合」 |
| **SLO**(目標) | SLI の目標値(社内向け) | 「30日間で 99.9% 成功」 |
| **SLA**(契約) | 守れなければ返金などがある約束(社外向け) | 「月間 99.5% を下回ったら返金」 |
| **エラーバジェット** | SLO までの「失敗してよい量」 | 99.9% なら 30日で約43分ぶん |
- 100% を目標にしない。**どこまでなら失敗を許すか**を決めると、新機能を出す速さと安定性のバランスが取れる
- エラーバジェットを使い切りそうなら、新機能より安定化を優先する、という判断に使う
- 個人開発なら厳密な SLO は不要。「エラー率」「p95 の遅延」を見る習慣だけでも十分

## 何を計測するか決める手順
1. **ユーザーにとって大事な操作**を挙げる(ログイン・検索・購入・投稿)
2. それぞれの「成功」と「速さ」を数値にする(SLI)
3. その数値が悪くなったら気づけるようにする(ダッシュボード・アラート)
4. 悪くなったときに原因を辿れるよう、ログとトレースを仕込む

## 費用の考え方
- ログ・トレースは**量に比例して費用がかかる**(保存・取り込み)
- 対策: **サンプリング**(一部だけ記録)、ログレベルで出し分け、保存期間を決める、不要なログを出さない
- エラーと遅いリクエストは全部残し、正常なものは間引く、という考え方(テールサンプリング)もある
