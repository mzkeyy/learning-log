## メトリクスとは
**時間ごとに集計された数値**。ログより軽く、長期間の傾向やアラートに向く。
| 種類 | 意味 | 例 |
| --- | --- | --- |
| **カウンター** | 増え続ける数(リセットされない) | リクエスト数の累計、エラー数 → 「1分あたり」に直して見る |
| **ゲージ** | その時点の値(増減する) | メモリ使用量、キューの長さ、同時接続数 |
| **ヒストグラム** | 値の分布 | 応答時間 → p50・p95・p99 を計算できる |
- **ラベル(属性)**で分けて見られる: `route=/api/orders`、`status=500`、`region=tokyo`
- ラベルに**種類が無限にある値(ユーザー ID・リクエスト ID)を入れない**(カーディナリティ爆発。費用と性能が悪化)。それはログやトレースで見る

## 何を測るか
### RED(API・サービス向け)
| | 意味 | 例 |
| --- | --- | --- |
| **R**ate | 毎秒のリクエスト数 | `/api/*` が 50 req/s |
| **E**rrors | 失敗の数・割合 | 5xx が 0.3% |
| **D**uration | 応答時間の分布 | p95 が 280ms |

### USE(サーバー・DB などの資源向け)
| | 意味 | 例 |
| --- | --- | --- |
| **U**tilization | 使用率 | CPU 60%、DB 接続 40/100 |
| **S**aturation | 待ちが出ているか | キューの長さ、待機中のリクエスト |
| **E**rrors | 資源のエラー | ディスクのエラー、接続拒否 |

### 業務の指標も
- 登録数・注文数・決済成功率・AI の利用トークン数など。**急に 0 になったら障害**のことがある(エラーが出ない種類の故障に気づける)

## 平均ではなくパーセンタイル
```
100件のリクエストのうち 95件が 100ms、5件が 5秒
  平均  = 345ms   ← 「まあまあ速い」に見える
  p50   = 100ms   ← 半分の人の体感
  p99   = 5秒     ← 一部の人はとても遅い(遅い人が 5% を超えると p95 も跳ね上がる)
```
- **p95・p99** を見ると「遅い目に遭っている人」に気づける
- 遅いのは大口顧客や重いページのことが多い。平均では埋もれる

## ダッシュボード
- 1画面目は**ユーザー目線の指標**だけ(リクエスト数・エラー率・p95・主要な業務指標)
- 詳細(資源・各依存先)は2画面目以降に
- **デプロイの時刻**を重ねて表示すると、変更が原因かすぐわかる
- 道具: Grafana、Datadog、CloudWatch ダッシュボード、Cloudflare のダッシュボード(Workers のメトリクス)

## アラート設計
### 良いアラートの条件
- **ユーザーに影響がある**ときに鳴る(症状にアラート、原因ではなく)
- 鳴ったら**すぐ何かする必要がある**(何もしなくていい通知はアラートにしない)
- 何を見ればいいか書いてある(ダッシュボードや手順書へのリンク)
| 良い例(症状) | 悪い例(原因・ノイズ) |
| --- | --- |
| 5分間のエラー率 > 2% | CPU 使用率 > 80%(負荷が高くても応答は正常かもしれない) |
| p95 > 1秒が10分続く | 1件でも 500 が出たら通知 |
| 外からの死活監視が2回連続失敗 | ディスク 70%(週次レポートで十分) |
| SLO のエラーバジェットの消費が速い | 夜中のバッチの一時的な遅延 |

### 通知の段階
| 重さ | 通知先 | 例 |
| --- | --- | --- |
| 緊急(今すぐ) | 電話・プッシュ通知 | サイトが落ちた、決済が全部失敗 |
| 営業時間内 | Slack・チケット | エラー率がじわじわ上昇 |
| 記録だけ | ダッシュボード・週次レポート | 容量が徐々に増加 |
- アラートが多すぎると**慣れて無視する**(アラート疲れ)。鳴ったのに何もしなかったアラートは見直すか消す

### SLO を使ったアラート(バーンレート)
- 「エラーバジェットを、このペースだと何日で使い切るか」で鳴らす
- 短い時間(1時間)と長い時間(6時間など)の両方で速い消費を見ると、一時的なノイズで鳴りにくい
- 個人開発ではまず「エラー率」と「死活監視」の2つで十分

## 外からの監視(合成監視)
- 外部のサービスから定期的に URL にアクセスして、**応答と中身**を確認する(死活監視)
- 例: UptimeRobot、Better Stack、Checkly、Datadog Synthetics、CloudWatch Synthetics
- ログイン → 検索 → 購入のような**操作の流れ**を定期実行するもの(E2E 監視)もある
- 中から見えない障害(DNS・証明書切れ・CDN)に気づける → [[DNS]] / [[HTTP・HTTPS・TLS]]

## 障害が起きたら
1. **影響を確認**(どの機能・何割のユーザー)してステータスを周知
2. **直前の変更を疑う**(デプロイ・設定変更)→ まず**ロールバック**で止血 → [[Cicdパイプライン]]
3. メトリクス → トレース → ログの順に原因を絞る
4. 落ち着いたら**振り返り**(ポストモーテム): 何が起きたか・なぜ気づくのが遅れたか・再発防止。個人を責めない
