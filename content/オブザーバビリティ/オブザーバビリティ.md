**本番で動いているシステムの中で何が起きているかを、外に出したデータ(ログ・メトリクス・トレース)から理解できる状態**のこと。日本語では「可観測性」。昔ながらの「監視(落ちていないか見張る)」を広げた考え方で、「**なぜ遅いのか・なぜ失敗したのか**」まで答えられるようにする。

OpenTelemetry・Google SRE 本・各サービスの公式ドキュメント(**2026年10月時点**)を元に、Web アプリを作る立場で整理したノート群の入口。

## 3本柱(+ α)
| 種類 | 何か | 答えられる問い | 例 |
| --- | --- | --- | --- |
| **ログ** | 出来事の記録(1件ずつ) | 「この時、何が起きた?」 | `order_created orderId=123 userId=u_1` |
| **メトリクス** | 数値の時系列(集計済み) | 「全体として正常? 増えてる?」 | リクエスト数、エラー率、遅延の p95 |
| **トレース** | 1リクエストの通り道と各処理の時間 | 「どこで遅い・どこで失敗?」 | API → DB 120ms → 外部 API 2s |
| エラー追跡 | 例外をまとめて通知 | 「どんなエラーが何回、誰に?」 | Sentry |
| プロファイル | CPU・メモリの使われ方 | 「どの関数が重い?」 | |

## 押さえどころ
- **ログは JSON(構造化ログ)**で出す。後から検索・集計できる
- 全ログに **リクエスト ID / トレース ID** を付けて、1つのリクエストの記録をつなげられるようにする
- 平均ではなく**パーセンタイル(p95・p99)**で遅延を見る
- アラートは「**ユーザーが困っていること**」(エラー率・遅延・SLO)に対して鳴らす。CPU 使用率だけで夜中に起こさない
- 標準規格の **OpenTelemetry** で計測しておくと、見る道具(Datadog・Grafana・Honeycomb など)を後から替えられる
- **パスワード・トークン・個人情報をログに出さない**
- まずは「エラー追跡(Sentry など)+ プラットフォームのログ(Cloudflare / CloudWatch)」から始めれば十分

## 小さく始める順番
1. エラーを通知で受け取る(Sentry、Cloudflare の Issues など)
2. 構造化ログ + リクエスト ID
3. 稼働監視(外から定期的にアクセスして落ちていないか)
4. 主要な指標のダッシュボード(リクエスト数・エラー率・p95)
5. トレース(遅い原因を追いたくなったら)
6. SLO とアラートの整理(運用する人が増えたら)
