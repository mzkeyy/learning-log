**コードが期待どおりに動くことを、コードで自動的に確かめる仕組み**。手で画面を触って確認する代わりに、変更のたびに数秒〜数分で「壊していないか」がわかる。AI にコードを書かせるほど、AI が出したものを確かめる手段として価値が上がる。

Vitest・Playwright の公式ドキュメント(**2026年10月時点。Vitest 5.0、Playwright 1.64**)を読んで、TypeScript の Web アプリを前提に整理したノート群の入口。

## 種類と道具の早見表
| 種類 | 何を確かめる | 速さ | 道具 |
| --- | --- | --- | --- |
| **単体テスト** | 関数・クラス1つ | とても速い | Vitest |
| **結合テスト** | API のエンドポイント、DB とのやり取り | 速い | Vitest + `app.request()` / テスト用 DB / MSW |
| **コンポーネントテスト** | 画面の部品の表示と操作 | 速い〜普通 | Vitest(Browser Mode)+ Testing Library |
| **E2E テスト** | 本物のブラウザでの一連の操作 | 遅い | Playwright |
| 型チェック | 型の矛盾 | 速い | `tsc --noEmit` → [[TypeScript]] |
| 静的解析 | 書き方の問題 | 速い | ESLint / Biome |

## 押さえどころ(2026年10月時点)
- **Vitest** が TypeScript のテストの第一候補(Vite の設定をそのまま使える、Jest とほぼ同じ書き方)。v5 は Node.js 22.12 以上・Vite 6.4 以上が必要
- E2E は **Playwright**
- 「**実装ではなく振る舞い**」をテストする。内部の変数名を変えただけで壊れるテストは悪いテスト
- 画面は**ユーザーと同じ方法で探す**(役割・ラベル・表示テキスト)。CSS のクラス名で探さない
- 外部 API はテストで本物を呼ばない(MSW などで置き換える)
- E2E は重要な流れ(ログイン・購入など)に絞る。大半は速いテストで押さえる
- **CI で毎回回す**。落ちたテストを放置しない → [[Cicdパイプライン]]

## 最小の例
```ts
// sum.ts
export const sum = (a: number, b: number) => a + b

// sum.test.ts
import { describe, it, expect } from 'vitest'
import { sum } from './sum'

describe('sum', () => {
  it('2つの数を足す', () => {
    expect(sum(1, 2)).toBe(3)
  })
})
```
```bash
npm install -D vitest
npx vitest        # 監視モード(保存するたびに再実行)
npx vitest run    # 1回だけ(CI 向け)
```
