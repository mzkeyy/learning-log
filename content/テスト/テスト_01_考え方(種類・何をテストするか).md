## なぜテストを書くか
- **変更が怖くなくなる**: 直したら別の場所が壊れた、にすぐ気づける(リファクタリングできる)
- **仕様が残る**: 「この関数は何をするか」がテストを読めばわかる
- **AI の出力を確かめられる**: AI が書いたコードが要件を満たすか、テストで判定できる。AI 自身にテストを回させて直させることもできる → [[07_ベストプラクティス]]
- 手で確認するより速く、毎回同じ品質で確認できる

## テストの種類
```
            ▲ 遅い・高い・壊れやすい / 本物に近い
           ╱ ╲
          ╱E2E╲          ← 重要な流れだけ(ログイン・購入)
         ╱─────╲
        ╱ 結合  ╲        ← API・DB・コンポーネント。ここを厚く
       ╱─────────╲
      ╱   単体    ╲      ← 計算・変換・判定のロジック
     ╱─────────────╲
    ╱ 型・静的解析  ╲    ← TypeScript・ESLint(書いた瞬間に見つかる)
   ▼ 速い・安い
```
| 種類 | 範囲 | 例 |
| --- | --- | --- |
| 静的 | コードを動かさずに | 型エラー、未使用の変数 |
| 単体 | 関数・クラス1つ | 「税込み価格の計算」「日付の表示形式」 |
| 結合 | いくつかの部品のつながり | 「POST /orders で DB に保存され 201 が返る」 |
| コンポーネント | 画面の部品 | 「ボタンを押すと件数が増える」 |
| E2E | 本物のブラウザでアプリ全体 | 「ログイン → カートに入れる → 購入完了」 |
- 昔は「単体を一番多く」(ピラミッド)と言われたが、Web アプリでは**結合テストを厚く**(トロフィー型)という考え方も広く使われる。実際の使われ方に近いので、少ない数で安心感が高い
- E2E は遅く不安定になりやすいので、**本当に大事な流れ**に絞る

## 何をテストするか
| テストする | テストしない(しなくてよい) |
| --- | --- |
| 業務のルール(料金計算・権限・状態の変化) | ライブラリやフレームワーク自体の動き |
| 境界の値(0件・上限・空文字・期限ぎりぎり) | 見た目の細かい位置(必要なら見た目の比較テスト) |
| エラーの時の動き(入力不正・外部 API の失敗) | 単純な受け渡しだけのコード |
| 過去に出たバグ(**再発防止**) | private な関数の中身 |
| 権限(他人のデータが見えない) → [[Webセキュリティ対策]] | |

### 振る舞いをテストする
```ts
// ❌ 実装の詳細をテスト: 内部の書き方を変えると壊れる
expect(cart.items.length).toBe(1)
expect(cart._recalculate).toHaveBeenCalled()

// ✅ 振る舞いをテスト: 外から見た結果だけ
cart.add({ id: 'p1', price: 1000 }, 2)
expect(cart.total()).toBe(2000)
```
- 「ユーザー(または呼び出す側)から見て何が起きるか」を確かめる

## 良いテストの条件
| 条件 | 意味 |
| --- | --- |
| 速い | 遅いと回さなくなる |
| 独立 | 順番や他のテストに左右されない。毎回データを用意して片付ける |
| 繰り返せる | いつ・どこで実行しても同じ結果(時刻・乱数・ネットワークに左右されない) |
| 読める | 失敗したとき、何が壊れたか名前とメッセージでわかる |
| 意味がある | 壊れたら本当に問題がある(誤って落ちない、壊れても通らない) |

### 書き方の型: Arrange-Act-Assert
```ts
it('在庫が足りないと注文できない', () => {
  // Arrange(準備)
  const stock = new Stock({ p1: 1 })
  // Act(実行)
  const result = stock.reserve('p1', 2)
  // Assert(確認)
  expect(result).toEqual({ ok: false, reason: 'out_of_stock' })
})
```
- テスト名は「**〜のとき〜になる**」と仕様の文章にする

## テストしやすいコード
- **計算と入出力を分ける**: 料金計算は純粋な関数にして、DB や API の呼び出しは外側に置く
- **依存を引数で受け取る**: 時刻(`now`)、乱数、DB クライアント、外部 API クライアントを外から渡せると、テストで差し替えやすい
- 1つの関数に多くの仕事をさせない
- → 設計の考え方は [[DDD_05_アーキテクチャ(レイヤード・オニオン・クリーン・CQRS)]] と同じ方向

```ts
// ❌ 中で現在時刻を取る → テストのたびに結果が変わる
export const isExpired = (expiresAt: Date) => expiresAt < new Date()

// ✅ 時刻を受け取る → テストで好きな時刻を渡せる
export const isExpired = (expiresAt: Date, now: Date) => expiresAt < now
```

## TDD(テスト駆動開発)
1. 失敗するテストを先に書く(Red)
2. それを通す最小のコードを書く(Green)
3. きれいに整える(Refactor)
- 仕様がはっきりしているロジックや、バグ修正(まず再現するテストを書く)に向く
- **AI に頼むときも有効**: 「まずテストを書いて、失敗を確認してから実装して」と指示すると、ゴールがはっきりする

## カバレッジは目安
- 「何%の行が実行されたか」。**高くても良いテストとは限らない**(確認していないテストでも数字は上がる)
- 「テストされていない重要な場所」を見つけるために使う。100% を目標にしない
