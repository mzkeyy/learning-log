## 前提: 必ずどこかが壊れる
- ネットワークは切れる・遅くなる。外部 API は落ちる。DB は混む。デプロイは失敗する
- 目標は「壊れないこと」ではなく、**一部が壊れても全体が止まらない・すぐ戻せる**こと
- 一番怖いのは、**1つの遅い依存先が、全体を巻き込んで止めること**(連鎖障害)

## タイムアウト
```ts
const res = await fetch(url, { signal: AbortSignal.timeout(3000) })   // 3秒で諦める
```
- **全部の外部呼び出しにタイムアウトを付ける**(既定は「無限に待つ」ことが多い)
- タイムアウトがないと、遅い依存先を待つリクエストが溜まり、接続・メモリ・スレッドを使い切って自分も落ちる
- 値は依存先の普段の p99 より少し長めに。呼び出しの階層が深いほど、**内側を短く**(外側の締め切りを超えないように)

## リトライ
```ts
async function withRetry<T>(fn: () => Promise<T>, max = 3): Promise<T> {
  for (let attempt = 0; ; attempt++) {
    try {
      return await fn()
    } catch (e) {
      if (attempt >= max - 1 || !isRetryable(e)) throw e
      const backoff = Math.min(1000 * 2 ** attempt, 8000)          // 指数バックオフ
      await sleep(backoff / 2 + Math.random() * (backoff / 2))     // ジッター(ばらつき)
    }
  }
}
```
| 再試行してよい | 再試行しない |
| --- | --- |
| タイムアウト、接続エラー、429、502 / 503 / 504 | 400 / 401 / 403 / 404(何度やっても同じ) |
- **冪等な処理だけ**再試行する(決済などは冪等キーを付ける)→ [[アーキテクチャ設計_04_非同期処理とイベント駆動(キュー・Pub-Sub・冪等性)]]
- **指数バックオフ + ジッター**: 全員が同じタイミングで再試行すると、回復しかけた相手をまた潰す(リトライの嵐)
- 回数に上限。各層でそれぞれ3回リトライすると、3 × 3 × 3 = 27倍の呼び出しになる。**リトライは1か所で**
- 429 の `Retry-After` には従う
- Claude などの SDK は自動でリトライする機能を持っている → [[AIアプリ開発_02_Claude APIの基本(メッセージ・ストリーミング・モデル選択)]]

## サーキットブレーカー
**失敗が続く相手への呼び出しを、しばらく止める**仕組み(電気のブレーカーと同じ)。
```
閉(普段)── 失敗が一定以上 ──▶ 開(呼ばずにすぐ失敗を返す)
   ▲                                │ 一定時間後
   └──── 試しに呼んで成功 ◀── 半開(少しだけ試す)
```
- 落ちている相手を待ち続けない(自分を守る)、相手が回復する時間を作る(相手を守る)
- ライブラリ(opossum など)、サービスメッシュ、API Gateway の機能で実現
- 開いている間は、フォールバック(下)を返す

## 劣化運転(グレースフルデグラデーション)
**一部の機能が使えなくても、大事な機能は動かし続ける**。
| 壊れたもの | 代わりに |
| --- | --- |
| おすすめ表示のサービス | おすすめ欄を隠す・人気順の固定リストを出す |
| 検索エンジン | DB の簡易検索 / 「検索は一時的に使えません」 |
| 在庫の確認 API | キャッシュの値で表示し、購入時にだけ確認 |
| AI の機能 | 「現在混み合っています」+ 従来の機能 |
- **何が必須で、何が「無くても困らない」か**を事前に決めておく
- 画面側でも、エラー・空の状態を用意しておく → [[React_05_実務(構成・性能・型・AI開発)]]

## バルクヘッド(隔壁)
- 船の隔壁のように、**資源を分けて、1つの問題が全体に広がらないようにする**
- 例: 外部 API ごとに接続数・同時実行数の上限を分ける、重い処理用のワーカーを分ける、テナントごとに制限
- キューで負荷を受け止めるのも同じ発想

## 負荷を断る(ロードシェディング・バックプレッシャー)
- 処理しきれないときは、**全部を遅くするより、一部を早めに断る**(503 / 429)ほうが全体は守れる
- 優先度の低いリクエスト(分析・バッチ)から断る

## 単一障害点をなくす
| 単一障害点 | 対策 |
| --- | --- |
| サーバー1台 | 複数台 + ロードバランサー、複数 AZ |
| DB 1つ | スタンバイ(マルチ AZ)、バックアップと復元の練習 |
| 1つのリージョン | 重要なら複数リージョン(費用と相談) |
| 1人しかわからない運用 | 手順書(ランブック)、自動化 |
| 外部サービス1社 | 重要なら代替手段(通知を複数チャネルに等) |
→ [[SAA_08_高可用性・DR・移行(バックアップ・DR戦略・監視)]]

## デプロイを安全に
- 小さく頻繁にデプロイ → 何が原因かすぐわかる
- **すぐ戻せる**(ロールバック)。DB の変更は戻せる形で → [[PostgreSQLとDrizzle_03_マイグレーション(drizzle-kit・安全な変更)]]
- 段階的に出す: カナリア(一部の利用者だけ新しい版)、ブルーグリーン(新旧を切り替え)
- **機能フラグ**: コードは出しても機能はオフにしておき、問題があればフラグで止める
→ [[Cicdパイプライン]]

## 気づく・直す
- エラー率・遅延・依存先の状態を監視し、アラート → [[オブザーバビリティ_03_メトリクスとアラート]]
- ヘルスチェック: 「生きているか(liveness)」と「リクエストを受けられるか(readiness)」を分ける
- 障害のあとは振り返り(ポストモーテム)で、仕組みの改善につなげる
- わざと障害を起こして確かめる(カオスエンジニアリング)のは、基本ができてから
