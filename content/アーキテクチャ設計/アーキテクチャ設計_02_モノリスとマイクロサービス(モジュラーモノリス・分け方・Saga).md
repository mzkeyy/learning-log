## 3つの形
```
モノリス                モジュラーモノリス            マイクロサービス
┌──────────┐          ┌──────────────────┐         ┌─────┐ ┌─────┐ ┌─────┐
│ 全部が    │          │ 注文 │ 在庫 │ 会員 │         │ 注文 │ │ 在庫 │ │ 会員 │
│ 混ざって  │          │──────┼──────┼──────│         └──┬──┘ └──┬──┘ └──┬──┘
│ いる      │          │  境界を守った1つのアプリ │      DB│      DB│      DB│
└────┬─────┘          └────────┬─────────┘          (サービスごとに独立したデプロイ・DB)
     DB                        DB
```
| | モノリス | **モジュラーモノリス** | マイクロサービス |
| --- | --- | --- | --- |
| デプロイ | 1つ | 1つ | サービスごと |
| 内部の境界 | あいまいになりがち | **モジュールで明確** | ネットワークで強制 |
| DB | 1つ | 1つ(モジュールごとにテーブルを分ける) | サービスごと |
| 呼び出し | 関数 | 関数(公開されたインターフェースだけ) | ネットワーク(HTTP・gRPC・キュー) |
| 運用の手間 | 小 | 小 | **大**(監視・デプロイ・障害対応がサービスの数だけ) |
| 向く場面 | 小規模・試作 | **ほとんどのプロダクト** | 大きな組織で、チームが独立して速く動く必要がある |

## まずはモジュラーモノリス
- マイクロサービスの利点(境界が明確、変更が局所的)の多くは、**1つのアプリの中でモジュールを分けるだけ**で得られる
- モジュール = 業務の区切り(注文・在庫・会員・決済)。[[DDD_02_戦略的設計(境界づけられたコンテキスト・サブドメイン・コンテキストマップ)]] の境界づけられたコンテキストが目安
- ルール
  - モジュールの中身は外から直接使わない。**公開する関数(API)だけ**を通す
  - 他のモジュールのテーブルを直接読み書きしない
  - モジュール間の依存は一方向に。循環させない
- フォルダや [[モノレポ]] のパッケージで分け、lint・依存ルールのツールで境界を守る
- 境界がしっかりしていれば、**必要になったときに1つだけ切り出す**のが簡単

## マイクロサービスにする理由・しない理由
| 分ける理由(本物) | 分けない理由 |
| --- | --- |
| 多くのチームが同じコードで衝突し、デプロイが詰まる | チームが1〜2つ |
| 一部だけ負荷が桁違い(画像処理・検索)で、別にスケールしたい | 全体の負荷が小さい |
| 一部だけ別の言語・技術が必要 | 流行っているから |
| 障害を一部に閉じ込めたい(決済が落ちても閲覧はできる) | 業務の境界がまだわからない(作りながら変わる段階) |
- **分散システムは難しい**: ネットワークの失敗、データの整合性、テスト・デバッグ・監視の難しさが一気に増える
- 「分けたけど、全部同時にデプロイしないと動かない」は最悪の形(分散モノリス)

## 分け方
- **業務の境界で分ける**(注文・在庫・決済)。技術の層(フロント・API・DB)で分けない
- 1つの変更が**1つのサービスで完結する**ように。毎回複数のサービスを同時に直すなら、分け方が間違っている
- **データの持ち主は1つのサービス**。他のサービスは API かイベントで受け取る
- 小さすぎる分割(ナノサービス)は、通信と運用の費用ばかり増える

## サービス間の通信
| 方式 | 例 | 向く場面 |
| --- | --- | --- |
| 同期(リクエスト・レスポンス) | HTTP / REST、gRPC | すぐ結果が必要(在庫の確認) |
| **非同期(メッセージ・イベント)** | キュー、Pub/Sub | 結果をすぐ待たなくていい(メール送信・集計)、他のサービスに知らせる |
- 同期の呼び出しが**連鎖**すると、1つの遅れ・障害が全体に広がる(全部のサービスが元気でないと動かない)
- できるだけ**非同期**で疎結合に → [[アーキテクチャ設計_04_非同期処理とイベント駆動(キュー・Pub-Sub・冪等性)]]
- 同期で呼ぶなら、タイムアウト・リトライ・サーキットブレーカー → [[アーキテクチャ設計_06_障害に強い設計(タイムアウト・リトライ・サーキットブレーカー)]]

## 分散トランザクションと Saga
DB が分かれると、「注文を作る・在庫を減らす・決済する」を**1つのトランザクションでまとめられない**。
```
Saga(各サービスが自分の処理を確定し、失敗したら「打ち消す処理」を順に実行)

注文作成 ─▶ 在庫確保 ─▶ 決済 ✗失敗
                ▲            │
                └─ 在庫を戻す ◀┘  ← 補償トランザクション
   注文をキャンセル ◀──────────┘
```
| 方式 | 内容 |
| --- | --- |
| コレオグラフィ | 各サービスがイベントを見て、自分で次の処理をする。中央なし。流れが追いにくい |
| オーケストレーション | 指揮役(ワークフロー)が順に指示する。流れが見える。AWS Step Functions、Temporal、Cloudflare Workflows |
- 途中の状態(在庫は確保したが決済前)が**一時的に見える**ことを前提にする(結果整合性)
- 補償の処理も失敗しうる → 再試行と人の対応の手順も用意する
