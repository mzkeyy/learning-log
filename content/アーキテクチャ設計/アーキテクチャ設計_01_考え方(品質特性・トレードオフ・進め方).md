## アーキテクチャとは
- **後から変えるのが大変な、重要な決定**の集まり(言語・フレームワーク、システムの分け方、データの持ち方、同期か非同期か、どこで動かすか)
- 機能(何ができるか)ではなく、**品質(どう動くか)**を決めるもの
- 一度決めて終わりではなく、規模や要件の変化に合わせて**育てる**もの

## 品質特性(〜性)
アーキテクチャで決まるのは主にこれら。全部を最高にはできないので、**優先順位を決める**。
| 品質特性 | 意味 | 問いの例 |
| --- | --- | --- |
| **性能** | 速さ・処理量 | p95 で何 ms? 毎秒何件? |
| **スケーラビリティ** | 負荷が増えても対応できるか | アクセスが10倍になったら? |
| **可用性** | 止まらないか | 年間どれだけ止まってよい?(99.9% = 約8.8時間) |
| **信頼性・耐障害性** | 壊れても正しく動き続けるか | DB が落ちたら? 外部 API が遅いと? |
| **セキュリティ** | 守れるか | 誰が何にアクセスできる? → [[Webセキュリティ対策]] |
| **保守性・変更容易性** | 直しやすいか | 新機能を何日で出せる? |
| **観測可能性** | 中で何が起きているかわかるか | 障害の原因を何分で特定できる? → [[オブザーバビリティ]] |
| **費用** | お金 | 月にいくら? 使った分だけ? |
| **開発のしやすさ** | チームが速く安全に作れるか | 新しい人が何日で開発できる? |
- 「速く・安く・止まらない・すぐ作れる」を全部はできない。たとえば**可用性を上げると費用が増える**

## トレードオフの例
| 選択 | 得るもの | 失うもの |
| --- | --- | --- |
| マイクロサービス | チームごとの独立したデプロイ・スケール | 運用の複雑さ、分散の難しさ |
| キャッシュ | 速さ・DB の負荷減 | データが古い可能性、整合性の管理 |
| 非同期(キュー) | 応答の速さ、ピークの吸収 | 結果がすぐ確定しない、デバッグが難しい |
| 複数リージョン | 可用性 | 費用、データの整合性 |
| サーバーレス | 運用の手間・アイドル時の費用 | コールドスタート、実行時間の制限、ベンダーへの依存 |
| 正規化した DB | 整合性 | 読み取りの JOIN の重さ |

## 決め方の流れ
1. **要件を集める**: 利用者数・アクセスのピーク・データ量・止まってよい時間・予算・チームの人数とスキル・締め切り
2. **優先する品質特性を3つ程度に絞る**(例: 開発の速さ > 費用 > 性能)
3. **選択肢を2〜3案出して比べる**(表にする)
4. **一番シンプルで要件を満たす案**を選ぶ
5. **決めた理由を記録**する → [[アーキテクチャ設計_07_設計ドキュメントとADR]]
6. 作って、計測して、見直す

### 数字で見積もる(概算)
| 前提 | 計算 |
| --- | --- |
| 1日 10万人 × 1人 20リクエスト | 200万リクエスト / 日 |
| 1日 = 約 8.6万秒 | 平均 約 23 リクエスト / 秒 |
| ピークは平均の 5〜10倍 | ピーク 約 100〜250 リクエスト / 秒 |
- 多くの個人・小規模のサービスは、**1台のサーバー + 1つの DB で十分**な規模。大げさな構成はいらない
- 覚えておくと便利な目安: メモリの読み取り ≪ SSD ≪ 同じデータセンター内の通信(〜0.5ms)≪ 大陸間の通信(〜150ms)

## 進化的アーキテクチャ
- 最初から完璧を目指さない。**変更しやすい形**にしておき、必要になったら変える
- **戻しにくい決定**(データベースの種類、外部公開の API の形、データの持ち方)ほど慎重に、**戻しやすい決定**(ライブラリ、内部の構造)は素早く
- 境界(モジュール・インターフェース)をはっきりさせておくと、後で分割・置き換えがしやすい
- 大きな作り直しより、**少しずつ置き換える**(Strangler Fig パターン: 新しい仕組みで一部ずつ包んで、古いものを減らしていく)

## コンウェイの法則
> システムの構造は、それを作る組織のコミュニケーション構造に似る
- チームが1つなら、サービスを細かく分けても運用が大変になるだけ
- 逆に、チームの分け方を先に決めて、それに合うアーキテクチャにする考え方もある(逆コンウェイ戦略)
