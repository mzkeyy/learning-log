## スケールの2つの方向
| | 垂直スケール(スケールアップ) | 水平スケール(スケールアウト) |
| --- | --- | --- |
| 方法 | 1台を強くする(CPU・メモリを増やす) | 台数を増やす |
| 長所 | 簡単。アプリを変えなくていい | 上限がほぼない、1台が落ちても続く |
| 短所 | 上限がある、止めて入れ替え | **アプリが状態を持たない**必要がある |
- まずは垂直、足りなくなったら水平。多くのサービスはかなり先まで垂直で足りる
- 水平にするには: セッション・アップロードファイル・キャッシュを**サーバーの外**(DB・Redis・S3)に出す(ステートレス) → [[Docker_04_本番とデプロイ(レジストリ・脆弱性・実行先)]]
- サーバーレス(Lambda・Workers・Cloud Run)は、水平スケールを自動でやってくれる

## ボトルネックはたいてい DB
アプリのサーバーは増やせても、DB は簡単に増やせない。順番に手を打つ。
| 段階 | 手 |
| --- | --- |
| 1 | **遅いクエリを直す・インデックス**(一番効く)→ [[PostgreSQLとDrizzle_04_実務(トランザクション・インデックス・接続・性能)]] |
| 2 | N+1 をなくす → [[N+1]] |
| 3 | **キャッシュ**で DB への読み取りを減らす(下) |
| 4 | **リードレプリカ**: 読み取り専用のコピーに読み取りを分ける(書き込み直後に読むと古いことがある) |
| 5 | 接続プール・プーラーで接続数を抑える |
| 6 | DB を大きくする(垂直) |
| 7 | 機能ごとに DB を分ける・**シャーディング**(データを複数の DB に分割。難しいので最後の手段) |
- 用途で DB を使い分ける: 全文検索は検索エンジン、セッション・ランキングは Redis、ファイルは S3 → [[SAA_06_データベース(RDS・Aurora・DynamoDB・ElastiCache)]]

## キャッシュ
**一度計算・取得した結果を、速い場所に一時的に置いて使い回す**。
| 層 | 例 | 置くもの |
| --- | --- | --- |
| ブラウザ | `Cache-Control` | 静的ファイル、変わらない API の結果 |
| **CDN** | CloudFront、Cloudflare | 画像・JS・CSS、公開ページの HTML |
| アプリのメモリ | プロセス内の Map・LRU | 設定・小さなマスタ(台数分バラバラになる点に注意) |
| **分散キャッシュ** | Redis(ElastiCache・Upstash)、Cloudflare KV | DB の結果、セッション、計算結果 |
| DB 自身 | バッファキャッシュ | 自動 |
→ [[Webパフォーマンスとアクセシビリティ_02_速くする方法(画像・フォント・JS・キャッシュ)]]

### 読み方・書き方のパターン
```ts
// Cache-Aside(一番よく使う): 無ければ DB から取ってキャッシュに入れる
async function getProduct(id: string) {
  const cached = await redis.get(`product:${id}`)
  if (cached) return JSON.parse(cached)

  const product = await db.query.products.findFirst({ where: eq(products.id, id) })
  await redis.set(`product:${id}`, JSON.stringify(product), { EX: 300 })   // 5分
  return product
}

// 更新したらキャッシュを消す
async function updateProduct(id: string, input: Partial<Product>) {
  await db.update(products).set(input).where(eq(products.id, id))
  await redis.del(`product:${id}`)
}
```
| パターン | 内容 |
| --- | --- |
| **Cache-Aside** | 読むときに無ければ入れる。更新時は消す |
| Write-Through | 書くときに DB とキャッシュの両方へ |
| Write-Behind | キャッシュに書いて、後で DB へ(速いが消えるリスク) |

### キャッシュの難しさ
| 問題 | 対策 |
| --- | --- |
| **古いデータ** | TTL(有効期限)、更新時に削除。「どれくらい古くてもいいか」を決める |
| 個人のデータが他人に見える | キャッシュのキーにユーザー ID、`Cache-Control: private` |
| キャッシュが一斉に切れて DB に殺到(Thundering Herd) | 期限をばらつかせる、1つだけ取りに行かせる(リクエストの合流)、期限切れでも古いものを返しつつ裏で更新(stale-while-revalidate) |
| キャッシュが落ちたら DB が耐えられない | キャッシュなしでも最低限動く容量を確保 |
- 「計算機科学で難しいのは、キャッシュの無効化と名前付けだけ」と言われるほど難しい。**本当に遅いところだけ**に使う

## 負荷を分散する
- **ロードバランサー**: 複数のサーバーに振り分け、ヘルスチェックで壊れたものを外す → [[SAA_03_ネットワーク(VPC・ELB・Route 53・CloudFront)]]
- **CDN**: 利用者の近くから静的なものを返す
- **キュー**: ピークを溜めて平らにする → [[アーキテクチャ設計_04_非同期処理とイベント駆動(キュー・Pub-Sub・冪等性)]]

## レート制限
使われすぎ・攻撃・暴走から守る。
| 方式 | 内容 |
| --- | --- |
| 固定窓 | 「1分あたり100回」。窓の境目に集中しうる |
| スライディング窓 | 直近60秒で数える |
| **トークンバケット** | 一定の速さでトークンが溜まり、1リクエストで1つ使う。短い集中は許す |
- キーは IP・ユーザー ID・API キー。ログイン・パスワードリセット・AI の API は特に厳しく
- 超えたら **429 + `Retry-After`**
- 置き場所: CDN / WAF(Cloudflare・AWS WAF)、API Gateway、アプリ(Redis で数える)

## CAP 定理と整合性
ネットワークが分断されたとき、**一貫性(C)と可用性(A)のどちらかを選ぶ**しかない、という定理。
| 選択 | 動き | 例 |
| --- | --- | --- |
| 一貫性を優先 | 最新を保証できないなら、エラーにする | 残高・在庫・予約 |
| 可用性を優先 | 少し古いかもしれない値でも返す | いいね数・閲覧数・おすすめ |
- **結果整合性**: 少し待てば全部が同じになる。多くの分散システム・キャッシュ・リードレプリカ・非同期処理はこれ
- 「どのデータは古くてもいいか」を**業務と相談して決める**のが大事

## 可用性の数字
| 可用性 | 年間の停止 | 月間の停止 |
| --- | --- | --- |
| 99% | 約3.65日 | 約7.3時間 |
| 99.9% | 約8.8時間 | 約43分 |
| 99.99% | 約53分 | 約4.3分 |
- 1つ増やすごとに費用と手間が大きく増える。**必要な数字を決めてから**構成を考える
- 冗長化: 複数の AZ、DB のスタンバイ、複数リージョン → [[SAA_08_高可用性・DR・移行(バックアップ・DR戦略・監視)]]

## システム設計の練習の流れ(面接でもよく出る)
1. 要件を確認(機能・利用者数・読み書きの比率・遅延・可用性)
2. 規模を概算(1秒あたりのリクエスト・データ量)→ [[アーキテクチャ設計_01_考え方(品質特性・トレードオフ・進め方)]]
3. API とデータモデルを決める
4. 高いレベルの構成図(クライアント・LB・アプリ・DB・キャッシュ・キュー)
5. ボトルネックを深掘り(DB・キャッシュ・ホットキー・単一障害点)
6. トレードオフを説明
