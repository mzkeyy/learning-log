## なぜ書くか
- 書くことで**自分の考えの穴に気づく**(頭の中では完璧に見える)
- 作る前に**レビューしてもらえる**(作った後に直すより何倍も安い)
- 半年後の自分・新しい人・AI が「**なぜこうなっているのか**」を知れる
- 決めた理由がないと、後から「とりあえず元に戻す」「同じ議論を繰り返す」が起きる

## 設計ドキュメント(Design Doc)
大きめの機能・変更を作る前に書く。長さより**判断に必要なことが書いてある**ことが大事。
```markdown
# 注文の非同期化(設計ドキュメント)

## 背景・課題
注文 API の p95 が 2.5 秒。メール送信と在庫連携を同期で呼んでおり、
在庫システムの障害で注文ができなくなる事故が月1回ある。

## 目標 / 目標にしないこと
- 目標: 注文 API の p95 を 500ms 以下に。在庫システムが落ちても注文は受け付ける
- 目標にしない: 在庫システム自体の改善、決済の非同期化

## 提案
注文確定後、Outbox 経由で「order.placed」イベントを発行し、
メール送信と在庫連携は SQS のワーカーで処理する。(構成図)

## 検討した別案
| 案 | 長所 | 短所 | 判断 |
| A. 今のまま、タイムアウトだけ短く | 簡単 | 在庫障害時は注文できない | 不採用 |
| B. 提案(キュー + Outbox) | 疎結合・速い | 仕組みが増える | 採用 |
| C. Step Functions で全体をワークフロー化 | 見える化 | 今の規模には大きい | 将来検討 |

## 詳細
API・データモデル・イベントの形・エラー処理・再試行・冪等性

## 移行・リリースの計画
機能フラグで段階的に。戻し方。

## リスク・未解決の点
- 在庫の確保が遅れる間に売り越す可能性 → 確保失敗時はキャンセルとお詫びメール

## 監視
キューの滞留数・DLQ の件数・処理の遅延
```
- 一番大事なのは**「検討した別案」と「目標にしないこと」**。ここがないと、なぜその案なのかが伝わらない
- 図は1枚あると理解が速い(Mermaid ならテキストで書けて、git で差分も見られる)

### 図の描き方(C4 モデル)
| レベル | 描くもの |
| --- | --- |
| 1. コンテキスト | システムと、利用者・外部システムの関係 |
| 2. コンテナ | アプリ・DB・キュー・BFF など、動く単位 |
| 3. コンポーネント | 1つのアプリの中のモジュール |
| 4. コード | クラス(普通は描かない) |
- 相手に合わせてレベルを選ぶ。全部を1枚に詰め込まない

## ADR(Architecture Decision Record)
**1つの重要な決定を、1つの短いファイルに記録する**。リポジトリの `docs/adr/` に連番で置くのが定番。
```markdown
# ADR-0007: ORM に Drizzle を採用する

- 状態: 採用(2026-10-26)
- 決めた人: 〇〇

## 背景
Workers と Node.js の両方で動き、型安全に PostgreSQL を扱いたい。
チームは SQL に慣れている。

## 決定
Drizzle ORM を使う。マイグレーションは drizzle-kit の generate + migrate。

## 検討した別案
- Prisma: 書きやすいが、エッジでの実行とバンドルサイズに不安があった
- Kysely: 軽いが、マイグレーションとスキーマ定義を別に用意する必要がある

## 結果(良いこと・悪いこと)
+ SQL に近く、学習コストが低い
+ スキーマから型とマイグレーションを作れる
- v1 で API が変わる予定。移行の手間が発生する
```
| ルール | 理由 |
| --- | --- |
| 短く(1ページ) | 書く・読むハードルを下げる |
| **書き換えない**(変えるときは新しい ADR を作り、古いものを「置き換え済み」に) | 当時の判断と経緯が残る |
| 「なぜ」と「別案」と「悪いこと」を書く | 良いことだけ書くと判断の材料にならない |
| コードの近くに置く | 変更と一緒にレビューできる |
- 何を ADR にするか: 後から変えにくい決定(言語・フレームワーク・DB・アーキテクチャの形・外部サービス・認証の方式)

## AI と設計
- 設計の相談相手として AI は強い。**要件・制約・優先する品質特性**を渡して、別案とトレードオフを出してもらう
- ただし AI は**流行りの大きな構成**(マイクロサービス・Kubernetes・イベントソーシング)を提案しがち。「チームの人数」「今の規模」「予算」を必ず伝える
- 決まった設計・ADR をリポジトリに置き、CLAUDE.md / AGENTS.md から参照させると、**AI がコードを書くときも設計に沿う** → [[04_CLAUDE.mdとメモリ]] / [[mdファイル使い分け]]
- 計画を先に書かせてから実装させる(Plan モード)と、設計の段階でずれを直せる → [[07_ベストプラクティス]]

## チェックリスト(設計レビュー)
- [ ] 解きたい課題と、目標・目標にしないことがはっきりしている
- [ ] 規模(リクエスト数・データ量)を概算した
- [ ] 別案を2つ以上比べ、選んだ理由がある
- [ ] 一番シンプルな案を検討した
- [ ] 障害時の動き(タイムアウト・リトライ・劣化運転)を考えた
- [ ] セキュリティ・個人情報・権限を考えた
- [ ] 監視とアラートを決めた
- [ ] 移行・リリース・戻し方の計画がある
- [ ] 重要な決定を ADR に残した
