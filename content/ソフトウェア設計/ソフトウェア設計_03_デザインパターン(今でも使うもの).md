## デザインパターンとは
**よくある設計の問題に対する、名前の付いた定番の解き方**。1994年の GoF(Gang of Four)の23パターンが有名。
- パターンを覚える一番の価値は**共通の言葉**になること(「ここは Strategy にしよう」で通じる)
- 多くは「Java のような言語で、関数を値として渡せなかった時代」の工夫。**TypeScript では関数1つで済む**ものも多い
- 問題がないのにパターンを当てはめない

## 今でもよく使うパターン
| パターン | 解く問題 | 身近な例 |
| --- | --- | --- |
| **Strategy** | アルゴリズムを差し替えたい | 支払い方法・料金計算・並び替えの基準 |
| **Factory** | 作り方が複雑・条件で作るものが変わる | 設定に応じたクライアントの生成 |
| **Adapter** | 形の違う API を、決めたインターフェースに合わせる | 外部の決済・メールサービスのラッパー |
| **Facade** | 複雑な仕組みの前に、簡単な窓口を置く | SDK のラッパー、`sendWelcomeEmail()` |
| **Decorator** | 元を変えずに機能を足す | ログ・キャッシュ・リトライを関数に巻き付ける、ミドルウェア |
| **Observer** | 変化を、関心のある相手に知らせる | イベント、`addEventListener`、状態の購読 |
| **Builder** | 引数の多いオブジェクトを段階的に組み立てる | クエリビルダー(Drizzle)、テストデータ |
| **Repository** | データの保存先を隠す | DB アクセスをまとめる → [[DDD_04_戦術的設計②(集約・リポジトリ・ドメインイベント)]] |
| **State** | 状態によって振る舞いが変わる | 注文の状態遷移(下書き → 支払済 → 発送済) |
| **Singleton** | インスタンスを1つだけ | DB の接続プール。ただしテストしにくくなるので注意 |
| **Middleware / Chain of Responsibility** | 処理を順番に通す | [[Hono_03_ミドルウェア(組み込み・自作・認証)]]、Express |

## Strategy
```ts
type ShippingStrategy = (weightKg: number) => number   // 関数の型 = インターフェース

const strategies: Record<'standard' | 'express' | 'pickup', ShippingStrategy> = {
  standard: (w) => 500 + w * 100,
  express: (w) => 1200 + w * 150,
  pickup: () => 0,
}

const shippingFee = (method: keyof typeof strategies, weightKg: number) => strategies[method](weightKg)
```
- クラスとインターフェースで書く代わりに、**関数の表(オブジェクト)**で十分
- 新しい配送方法 = 表に1行足すだけ(開放閉鎖の原則)

## Adapter
```ts
// アプリが期待する形
interface PaymentGateway {
  charge(input: { amountYen: number; customerId: string }): Promise<{ id: string }>
}

// 外部 SDK の形の違いを吸収する
export const stripeAdapter = (stripe: Stripe): PaymentGateway => ({
  async charge({ amountYen, customerId }) {
    const intent = await stripe.paymentIntents.create({ amount: amountYen, currency: 'jpy', customer: customerId })
    return { id: intent.id }
  },
})
```
- 外部サービスの API が変わっても、**直すのは Adapter だけ**
- テストでは偽物の `PaymentGateway` を渡せる
- AI の API を複数社から選べるようにするのも同じ考え方 → [[AIアプリ開発_06_画面との連携(AI SDK・Hono・Next.js)]]

## Decorator(関数を包む)
```ts
const withRetry = <A extends unknown[], R>(fn: (...a: A) => Promise<R>, times = 3) =>
  async (...args: A): Promise<R> => {
    let lastError: unknown
    for (let i = 0; i < times; i++) {
      try { return await fn(...args) } catch (e) { lastError = e; await sleep(2 ** i * 100) }
    }
    throw lastError
  }

const fetchUserWithRetry = withRetry(fetchUser)
```
- ログ・計測・キャッシュ・リトライ・認可チェックを、**元の関数を変えずに**足せる
- Web フレームワークのミドルウェアも同じ発想

## Observer(イベント)
```ts
type Events = { orderPlaced: { orderId: string; userId: string } }

const listeners: { [K in keyof Events]?: ((e: Events[K]) => void)[] } = {}

export const on = <K extends keyof Events>(type: K, fn: (e: Events[K]) => void) =>
  (listeners[type] ??= []).push(fn)
export const emit = <K extends keyof Events>(type: K, e: Events[K]) =>
  listeners[type]?.forEach((fn) => fn(e))

on('orderPlaced', (e) => sendConfirmationEmail(e))
on('orderPlaced', (e) => addLoyaltyPoints(e))
emit('orderPlaced', { orderId: 'o_1', userId: 'u_1' })
```
- 注文の処理が、メール・ポイントのことを知らなくていい(結合が弱くなる)
- 代わりに**流れが追いにくく**なる。使いすぎ注意
- サービスをまたぐ場合はキュー・イベント駆動 → [[アーキテクチャ設計_04_非同期処理とイベント駆動(キュー・Pub-Sub・冪等性)]]

## State(状態遷移)
```ts
type Order =
  | { status: 'draft'; items: Item[] }
  | { status: 'paid'; items: Item[]; paidAt: Date }
  | { status: 'shipped'; items: Item[]; paidAt: Date; trackingNo: string }

const ship = (order: Extract<Order, { status: 'paid' }>, trackingNo: string): Order =>
  ({ ...order, status: 'shipped', trackingNo })   // paid 以外は型エラーで渡せない
```
- TypeScript では**判別可能なユニオン型**で、「この状態でしか呼べない操作」を型で表せる → [[TypeScript_03_型の組み立て(ユニオン・リテラル・interface・type)]]
- 状態が多く複雑なら、状態機械のライブラリ(XState など)

## 避けたほうがいいもの
| パターン・書き方 | 問題 | 代わりに |
| --- | --- | --- |
| Singleton をグローバル変数のように使う | どこからでも変更できる・テストで差し替えにくい | 依存性の注入で渡す |
| 何でも Factory・AbstractFactory | 読む量が増えるだけ | 普通に関数を呼ぶ |
| 深い継承の Template Method | 親を変えると全部に響く | Strategy・合成 |
| Service Locator(どこからでも依存を取り出す) | 依存が見えない | コンストラクタ・引数で受け取る |
