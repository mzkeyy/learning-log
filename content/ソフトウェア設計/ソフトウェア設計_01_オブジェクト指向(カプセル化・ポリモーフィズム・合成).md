## オブジェクト指向とは
**データと、そのデータを扱う処理を1つにまとめて(オブジェクト)、オブジェクト同士のやり取りでプログラムを組み立てる**考え方。
```ts
class BankAccount {
  #balance = 0                      // 外から直接触れない(private)

  deposit(amount: number) {
    if (amount <= 0) throw new Error('入金額は正の数')
    this.#balance += amount
  }

  withdraw(amount: number) {
    if (amount > this.#balance) throw new Error('残高不足')
    this.#balance -= amount
  }

  get balance() { return this.#balance }
}
```
- 「残高をマイナスにしない」というルールが**クラスの中に閉じている**。どこから使っても守られる

## 3つの柱
| 柱 | 意味 | うれしいこと |
| --- | --- | --- |
| **カプセル化** | 中身(データ)を隠し、決めた操作(メソッド)だけ公開する | ルールを1か所で守れる。中身を変えても使う側が壊れない |
| **ポリモーフィズム**(多態性) | 同じ呼び方で、相手によって違う動きをする | if / switch の分岐を減らし、種類を足しやすい |
| **継承** | 親クラスの機能を子クラスが引き継ぐ | コードの再利用(ただし使いすぎに注意 → 下) |

### カプセル化: 「尋ねるな、命じよ」
```ts
// ❌ 外から中身を取り出して判断・変更している
if (order.status === 'paid' && order.items.length > 0) {
  order.status = 'shipped'
  order.shippedAt = new Date()
}

// ✅ オブジェクトに頼む。ルールはオブジェクトの中
order.ship(new Date())
```
- データを公開して外で操作すると、同じルールがあちこちに散らばる(変更のたびに全部直す)
- TypeScript の `#field`(本当の private)や `readonly` を使う。getter / setter を全部の項目に付けるのは、カプセル化になっていない

### ポリモーフィズム: 分岐を型に置き換える
```ts
// ❌ 種類が増えるたびに switch を全部探して直す
function fee(method: 'card' | 'bank' | 'convenience', amount: number) {
  switch (method) {
    case 'card': return amount * 0.036
    case 'bank': return 0
    case 'convenience': return 200
  }
}

// ✅ 共通のインターフェースを満たす実装を差し替える
interface PaymentMethod {
  fee(amount: number): number
}
const card: PaymentMethod = { fee: (a) => a * 0.036 }
const bank: PaymentMethod = { fee: () => 0 }
const convenience: PaymentMethod = { fee: () => 200 }

const total = (method: PaymentMethod, amount: number) => amount + method.fee(amount)
```
- 新しい支払い方法は**新しい実装を足すだけ**。既存のコードは変えない(開放閉鎖の原則 → [[ソフトウェア設計_02_設計原則(SOLID・DRY・KISS・YAGNI・依存性の注入)]])
- ただし種類が少なく増えないなら、`switch` + ユニオン型の網羅チェックの方が素直なこともある → [[TypeScript_04_型の絞り込み(Narrowing)]]

## 継承より合成
```ts
// ❌ 継承の連鎖: 「鳥は飛ぶ」→ ペンギンが困る
class Bird { fly() { /* ... */ } }
class Penguin extends Bird { fly() { throw new Error('飛べない') } }

// ✅ 合成: 必要な能力を部品として持たせる
interface Flyer { fly(): void }
interface Swimmer { swim(): void }

class Duck { constructor(private flyer: Flyer, private swimmer: Swimmer) {} }
class Penguin { constructor(private swimmer: Swimmer) {} }
```
| | 継承 | 合成(委譲) |
| --- | --- | --- |
| 関係 | 「〜は〜の一種」(is-a) | 「〜は〜を持つ」(has-a) |
| 結合 | **親の変更が子全部に響く**(強い結合) | 部品を差し替えられる(弱い結合) |
| 向く場面 | 本当に一種で、親がほぼ変わらない(フレームワークの基底クラスなど) | **ほとんどの場合** |
- 継承は「コードを使い回したい」だけで使わない。階層が深くなると、どこで何が起きているか追えなくなる

## インターフェースに依存する
```ts
interface Mailer { send(to: string, subject: string, body: string): Promise<void> }

class SignupService {
  constructor(private mailer: Mailer) {}          // 具体的なメール送信の仕組みを知らない
  async signup(email: string) {
    // ...ユーザー作成
    await this.mailer.send(email, 'ようこそ', '...')
  }
}

// 本番は SES、テストは偽物
new SignupService(new SesMailer())
new SignupService({ send: async () => {} })
```
- 「何ができるか(インターフェース)」に依存し、「どう実装されているか」に依存しない
- これが依存性の注入(DI)。テストで差し替えられる → [[ソフトウェア設計_02_設計原則(SOLID・DRY・KISS・YAGNI・依存性の注入)]]
- TypeScript は**構造的型付け**なので、`implements` を書かなくても形が合えば使える → [[TypeScript_09_型システムの性質(構造的型付け・推論・satisfies)]]

## TypeScript でのクラスの使いどころ
| クラスが向く | 関数 + オブジェクトで十分 |
| --- | --- |
| 状態と、それを守るルールがある(口座・カート・注文) | 入力を受けて結果を返すだけの処理 |
| 同じインターフェースの実装を複数用意する | 設定値や定数のまとまり |
| フレームワークがクラスを求める(NestJS など) | React のコンポーネント・フック |
| 値オブジェクト・エンティティ → [[DDD_03_戦術的設計①(エンティティ・値オブジェクト・ドメインサービス)]] | ユーティリティ関数 |
- JavaScript / TypeScript では、**関数とモジュール(ファイル)**がカプセル化の単位としても十分に働く(export しないものは外から見えない)
