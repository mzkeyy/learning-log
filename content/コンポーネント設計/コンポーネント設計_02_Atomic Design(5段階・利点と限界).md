## Atomic Design とは
Brad Frost が2013年に提唱した、**UI を化学のたとえで5段階に分けて組み立てる**考え方。小さな部品から大きな部品へ、段階を踏んで画面を作る。
```
原子(Atoms) → 分子(Molecules) → 有機体(Organisms) → テンプレート(Templates) → ページ(Pages)
  ボタン          検索フォーム           ヘッダー                 一覧ページの骨組み          実データの入った画面
```

## 5つの段階
| 段階 | 意味 | 例 |
| --- | --- | --- |
| **原子** | これ以上分けられない最小の部品 | ボタン、入力欄、ラベル、アイコン、見出し |
| **分子** | 原子を組み合わせた、1つの役割を持つ小さなまとまり | 検索フォーム(ラベル + 入力欄 + ボタン)、フォームの1項目 |
| **有機体** | 分子・原子を組み合わせた、画面の独立した区画 | ヘッダー、商品カードの一覧、コメント欄、フッター |
| **テンプレート** | 有機体を配置した**ページの骨組み**(中身はダミー) | 「一覧ページ」のレイアウト |
| **ページ** | テンプレートに**実際のデータ**を入れたもの | 「スニーカーの検索結果」の画面 |
- 原子のさらに下に、**デザイントークン**(色・余白)を「素粒子」として置くことも多い → [[デザイントークン]]
- テンプレートとページは「コンポーネント」というより**画面の設計を確かめる段階**。データが入ると崩れる箇所(長い名前・0件・大量)がわかる

## うれしいこと
- **小さな部品から積み上げる**意識が持てる(画面ごとにバラバラな部品を作らない)
- デザイナーと開発者の**共通の言葉**になる(「これは分子として作ろう」)
- 部品の粒度を議論するきっかけになる
- テンプレート → ページで、**実データでの崩れ**を確認する習慣がつく

## つまずきやすいところ
| 問題 | 説明 |
| --- | --- |
| **分類で迷う** | 「この部品は分子? 有機体?」の議論に時間がかかる。人によって答えが違う |
| **フォルダの階層が実装と合わない** | `atoms/` `molecules/` に分けると、1つの機能のファイルがあちこちに散らばる |
| 移動が多い | 部品が育つと分子から有機体に「昇格」してフォルダを移すことに |
| データ・状態の扱いを決めていない | どの段階でデータを取得するか、業務のロジックをどこに置くかは Atomic Design の範囲外 |
| 「再利用できない部品」の居場所がない | 1画面でしか使わない部品まで、どこかの段階に分類しようとしてしまう |
- 提唱者自身も「**厳密な分類ではなく、考え方のモデル**」と述べている

## 今の使い方(現実的な落としどころ)
```
❌ 5段階のフォルダに機械的に分ける
src/components/atoms/  molecules/  organisms/  templates/

✅ 「共通の部品」と「機能の部品」で分け、共通の部品の中で大きさを意識する
src/
├── components/
│   ├── ui/          … 原子・分子に相当(Button・Input・Dialog・Field)← デザインシステムの部品
│   └── patterns/    … よく使う組み合わせ(SearchForm・EmptyState・DataTable)
├── features/
│   └── orders/
│       └── components/ … 有機体に相当(OrderList・OrderSummary)← 業務を知っている部品
└── app/ (routes/)  … テンプレート・ページに相当(レイアウトと画面)
```
| Atomic Design | 今のよくある置き場所 | 特徴 |
| --- | --- | --- |
| 原子・分子 | `components/ui/` | 業務を知らない、見た目と振る舞いだけ。どこでも使える |
| 有機体 | `components/patterns/` か `features/*/components/` | 共通なら patterns、業務を知っているなら features |
| テンプレート | `layout.tsx` などのレイアウト | ページの枠 |
| ページ | `app/` や `routes/` の画面 | データを取得して部品に渡す |
- 詳しい分け方 → [[コンポーネント設計_03_分け方(責務・層・置き場所)]]
- [[shadcn-ui]] の `components/ui/` は、まさに原子・分子の層

## 他の考え方
| 考え方 | 内容 |
| --- | --- |
| **ドメイン・機能単位**(Feature-based) | 業務の機能ごとにフォルダを作り、その中に部品・フック・API をまとめる |
| Feature-Sliced Design | `app / pages / widgets / features / entities / shared` の層と、依存の方向のルール |
| コロケーション | 使う場所の近くに置く。共通化が必要になってから移す |
- どれも「**共通のもの**」と「**機能のもの**」を分け、**依存の方向**(機能 → 共通。逆はダメ)を決めている点は同じ
