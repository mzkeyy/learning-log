## 2つの軸で分ける
```
                    見た目だけ(データを知らない)      データ・業務を知っている
共通(どこでも使う)   Button / Dialog / Field          (あまり作らない)
                    → components/ui                  
機能専用            OrderStatusBadge                 OrderList / CheckoutForm
                    → features/orders/components      → features/orders/components
```
- **共通の部品は業務を知らない**(`Button` は「注文」を知らない)。業務の言葉が入ったら機能側へ
- **データを取ってくる部品は少なく、上の方に**。下の部品は props で受け取るだけにすると、テスト・再利用がしやすい

## 見た目とロジックを分ける
### 昔: Presentational と Container
```tsx
// Container: データを取って渡すだけ
function OrderListContainer() {
  const { data } = useOrders()
  return <OrderList orders={data} />
}
// Presentational: 受け取って表示するだけ
function OrderList({ orders }: { orders: Order[] }) { /* ... */ }
```
- 考え方は今も有効だが、**フックが登場してからは、ロジックはカスタムフックに分ける**のが主流
### 今: カスタムフック + 表示の部品
```tsx
function useOrderFilters() {            // ロジック(状態・計算・URL)
  const [status, setStatus] = useState<OrderStatus | 'all'>('all')
  return { status, setStatus }
}

function OrderPage() {                  // 組み立て(データ取得はここか、フレームワークの loader / Server Components)
  const filters = useOrderFilters()
  const { data, isPending } = useOrders(filters.status)
  return <OrderList orders={data ?? []} loading={isPending} />
}
```
- **Server Components** が使えるなら、データ取得はサーバー側の部品で行い、操作が必要な部分だけをクライアントの部品にする → [[Next.js_03_Server ComponentsとClient Components]]

## ヘッドレス(振る舞いと見た目を分ける)
**振る舞い・アクセシビリティだけを提供し、見た目は持たない**部品・フック。
| ライブラリ | 特徴 |
| --- | --- |
| **Radix UI** | 定番。shadcn/ui の土台 |
| **Base UI** | MUI のチームによるヘッドレス部品(1.x)。shadcn/ui も対応 |
| React Aria(Adobe) | アクセシビリティと国際化がとても丁寧 |
| Ark UI | 状態機械ベース。React 以外にも |
| TanStack Table / Form | 表・フォームのロジックだけ |
- **モーダル・メニュー・タブ・コンボボックス・ツールチップ**は、キーボード操作・フォーカス管理・ARIA が難しい。**自作せずヘッドレス部品に見た目を乗せる** → [[Webパフォーマンスとアクセシビリティ_04_アクセシビリティの実装とチェック]]
- shadcn/ui は「ヘッドレス部品 + Tailwind の見た目」をコピーして自分のものにする仕組み → [[shadcn-ui_01_考え方と仕組み]]

## 分ける・分けないの基準
| 分ける | 分けない |
| --- | --- |
| **3回以上**同じ形が出てきた | 1回しか使わない(画面の中に書いたままでいい) |
| 名前を付けられるまとまりがある | 名前が付けられない(「Wrapper2」「Section」) |
| 状態ごとの確認・テストを単独でしたい | 分けると props のバケツリレーが増えるだけ |
| ファイルが長く(目安 200〜300行)、役割が複数ある | 見た目が似ているだけで、変わる理由が違う |
- **早すぎる共通化は危険**: 2つの画面の「似ている部品」を1つにすると、片方の変更のたびに if と props が増える(→ [[ソフトウェア設計_02_設計原則(SOLID・DRY・KISS・YAGNI・依存性の注入)]] の DRY の落とし穴)
- 迷ったら**使う場所の近く(コロケーション)に置き、本当に共通になったら移す**

## 状態をどこに置くか
| 状態 | 置き場所 |
| --- | --- |
| 開閉・hover など、その部品だけの状態 | 部品の中 |
| 兄弟の部品で共有 | 共通の親に持ち上げる |
| サーバーのデータ | TanStack Query / Server Components |
| 検索条件・タブ・ページ | URL |
| アプリ全体(テーマ・ログインユーザー) | Context / Zustand |
→ [[React_04_状態管理とデータ取得(Context・Zustand・TanStack Query)]]
- **共通の部品(`components/ui`)はアプリの状態を直接読まない**。必要な値は props で受け取る

## フォルダ構成の例
```
src/
├── app/ or routes/            # 画面・レイアウト(データを取って、機能の部品に渡す)
├── features/
│   ├── orders/
│   │   ├── components/        # OrderList, OrderStatusBadge(業務を知っている)
│   │   ├── hooks/             # useOrders, useOrderFilters
│   │   ├── api.ts
│   │   └── index.ts           # 外に公開するものだけ export
│   └── auth/
├── components/
│   ├── ui/                    # Button, Input, Dialog(デザインシステムの部品)
│   └── patterns/              # EmptyState, DataTable, PageHeader(業務を知らない組み合わせ)
├── hooks/                     # 共通のフック
└── lib/                       # 汎用の関数
```
### 依存のルール
```
app → features → components / hooks / lib
             ✗ features/orders → features/auth の中身を直接 import しない(公開した index.ts 経由)
             ✗ components/ui → features を import しない
```
- ルールは lint(import の制限)で機械的に守る → [[AIエンジニアリング_04_コーディングエージェントのハーネス(実践)]]
- モノレポなら共通の部品を `packages/ui` に → [[モノレポ_01_考え方(向き不向き・構成例)]]

## 命名
- 部品は**何であるか**で名前を付ける(`OrderSummary`)。見た目(`BlueBox`)や場所(`LeftColumn`)で付けない
- 共通の部品は業務の言葉を使わない(`Badge`)、機能の部品は業務の言葉を使う(`OrderStatusBadge`)
- ファイル名とエクスポート名を揃える。1ファイル1部品が基本(小さな補助部品は同じファイルでよい)
